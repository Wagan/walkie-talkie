ЗАДАНИЕ (Wagan's Team): TASK_lab02_rx_dma
Автор: Vagan Sarukhanov

КОНТЕКСТ

LAB02 (обмен между двумя китами по USART1, 115200 8N1) не принимала пакеты: rx=0 при
растущих fe и crc, в том числе при замыкании PA9 на PA10 на одной плате.

Причина установлена твоей же разведкой (TASK_uart_rx_reference): не настройки UART и
не обработка ошибок, а пакетная рассинхронизация. Приём фиксированной длины без
кадрирования и без точки ресинхронизации: единожды сдвинувшись на байт, приёмник
читает поток с неверного смещения, поэтому CRC не сходится ни у одного пакета.

Принято решение владельца: перейти на приём через HAL_UARTEx_ReceiveToIdle_DMA в
кольцевой буфер, по эталону ST — UART_ReceptionToIdle_CircularDMA. Это убирает окно
перезапуска, а событие простоя линии даёт естественную границу сообщения. Это же
целевая архитектура для LAB04, где по каналу пойдёт непрерывный звук.

ЧТО УЖЕ СДЕЛАНО ВЛАДЕЛЬЦЕМ В .ioc (код перегенерирован):
- добавлен DMA-запрос USART1_RX: DMA2 Stream 2, Peripheral To Memory, режим Circular,
  разрядность Byte для периферии и памяти, инкремент только по памяти, FIFO выключен;
- включено прерывание DMA2 stream2 (было включено автоматически);
- включено прерывание USART1 global interrupt (нужно для события IDLE);
- приоритеты обоих прерываний равны нулю.

ТЕКУЩАЯ ОШИБКА СБОРКИ, которую надо устранить в рамках этой задачи:
multiple definition of USART1_IRQHandler — раньше прерывание USART1 в .ioc включено не
было, и ты определил обработчик прямо в App/Labs/uart_link.c. Теперь CubeMX сгенерировал
свой обработчик в Core/Src/stm32f4xx_it.c. Убирать надо НАШ обработчик из uart_link.c,
сгенерированный оставить как есть.

ЗАДАЧА A. ПЕРЕВОД ПРИЁМА НА КОЛЬЦЕВОЙ DMA

Опора — эталон UART_ReceptionToIdle_CircularDMA из пакета. Прочитать его фактически и
следовать его архитектуре, а не изобретать свою.

1. Убрать из uart_link.c собственный USART1_IRQHandler и ручное включение прерывания
   USART1 в Lab_Init — теперь это делает сгенерированный код.
2. Приём запускать один раз через HAL_UARTEx_ReceiveToIdle_DMA на весь кольцевой
   буфер. Размер буфера выбрать осознанно и обосновать комментарием: он должен
   вмещать с запасом несколько пакетов, чтобы приложение успевало разбирать данные
   между событиями.
3. Разбор входящих данных вести в HAL_UARTEx_RxEventCallback, как в эталоне: хранить
   позицию последнего разобранного байта, забирать новый участок кольца, корректно
   обрабатывать переход через конец буфера.
4. Из колбэка не печатать. Только накопление данных и счётчики.

Обратить внимание: колбэк вызывается на трёх событиях — заполнение половины буфера,
заполнение буфера целиком и простой линии. Обработка должна быть одинаково корректной
во всех трёх случаях.


ЗАДАЧА B. СБОРКА ПАКЕТОВ ИЗ ПОТОКА

Кольцо даёт непрерывный поток байтов, и его надо разложить на пакеты.

Поскольку передатчик шлёт пакеты фиксированной длины с паузами между ними, событие
простоя линии естественно совпадает с границей пакета. Использовать это как основную
точку синхронизации.

Но полагаться только на паузу нельзя: в нагрузочном режиме пауз нет вовсе. Поэтому:

1. Реализовать простую сборку: накапливать байты, при наборе полного пакета проверять
   контрольную сумму.
2. Если контрольная сумма не сошлась — не выбрасывать весь буфер, а сдвинуться на один
   байт и попробовать снова. Это простейшая ресинхронизация, и её достаточно, чтобы
   восстановиться после единичного сбоя. Ограничить число попыток разумной величиной и
   описать логику комментарием.
3. Считать отдельным счётчиком, сколько раз потребовалась ресинхронизация — это
   полезная для студента цифра, показывающая устойчивость канала.

Полноценное кадрирование с маркерами и экранированием остаётся содержанием LAB03 —
здесь только минимальная ресинхронизация по контрольной сумме.


ЗАДАЧА C. ЧИСТКА

1. Устранить предупреждение сборки: 'loadStartMs' defined but not used — переменная
   нужна только нагрузочному режиму. Решить аккуратно, чтобы обе ветки режима
   компилировались без предупреждений.
2. Проверить весь файл на другие предупреждения, которые появятся после переделки.
3. Убедиться, что счётчики ошибок приёмника продолжают работать: в режиме DMA ошибки
   обрабатываются иначе, чем в режиме прерываний. По коду HAL проверить, что именно
   происходит при ошибке в DMA-режиме, и перезапускать приём, если это требуется.
   Вывод записать комментарием.
