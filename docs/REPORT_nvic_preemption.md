# Отчёт: разрешить вытеснение, аудио-выход выше приёмного USART2

Лечение по подтверждённому диагнозу (`REPORT_isr_deadline_probe.md`, `REPORT_rx_isr_offload.md`).
Вынос разбора из ISR (60dfbe6) уменьшил амплитуду (max опоздания 1367→1203 мкс), но частоту
срывов не изменил (0.68→0.71/с) — её задаёт геометрия фаз (5 мс кратно 1 мс + уход кварцев).
Структурный ход — вытеснение: дать аудио-выходу приоритет выше приёмного USART2, чтобы
пере-взвод не ждал длинный приёмный ISR.

Правки **только в `App/Labs/speech.c` (LAB07)**. Сборка LAB07/LAB00/LAB04 — **0 ошибок,
0 предупреждений**. Инструментовка probe A/B/C и вынос разбора из ISR сохранены. `.ioc`,
HAL/CMSIS/BSP, ThirdParty, circular-режим выхода, LAB04 — не трогались.

**Проверено на железе — ДЕФЕКТ ВЫЛЕЧЕН** (ulaw, `rate 8000`, 460800, ~10 мин): `probeA over=0`
при `calls=595323`, `max=1000 мкс` ровно, на слух чисто во всех интервалах, где раньше шли серии
(при прежней частоте 0.71/с ожидалось бы ~420 событий — получен ноль). `probeB max≈205 мкс` не
изменился (и не должен был). Побочно: собственный джиттер на простое (база `probeA max` была
1013–1021 при пороге 1031) исчез сразу после включения вытеснения — он тоже был помехой от чужих
обработчиков.

## Этап 1 — разведка

### 1. Где задаётся группа приоритетов

`Core/Src/stm32f4xx_hal_msp.c:75`: `HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_0)` —
**генерируемый CubeMX код, ВНЕ USER CODE** (стоит между `__HAL_RCC_*_CLK_ENABLE()` и
`USER CODE END MspInit 1`). Прямая правка здесь регенерацию из `.ioc` **не переживёт**.
Пользовательские секции есть (`USER CODE BEGIN MspInit 0` :68, `MspInit 1` :79) — туда override
поставить можно, но он всё равно жил бы в генерируемом файле.

**Выбранное место — App-код (`speech.c`, `configure_preemption()`), вызывается в конце
`Lab_Init` (LAB07).** Причины: App/ вне зоны CubeMX → переживает регенерацию; правка
LAB07-локальна (другие работы не трогаются); откат — удалением вызова. Вызывается ПОСЛЕ всех
MspInit (когда генерируемые приоритеты уже расставлены), поэтому переопределяет их.

### 2. Включённые прерывания и текущие приоритеты (все при GROUP_0 = вытеснения нет)

| Прерывание | IRQn | prio | Где задано |
|---|---|---|---|
| SysTick | `SysTick_IRQn` | 0 | `HAL_InitTick(TICK_INT_PRIORITY=0)` — `hal_conf.h:151`, `hal.c:264` |
| USART2 (IDLE/TX/ошибки) | `USART2_IRQn` | 0,0 | `hal_msp.c:133` (генер.) |
| USART2 RX DMA | `DMA1_Stream5_IRQn` | 0,0 | `Core/Src/main.c:227` (генер.) |
| Аудио-выход I2S3 DMA | `DMA1_Stream7_IRQn` | 0x0E | BSP `..._audio.c:598`, значение `..._audio.h:93` |
| Аудио-вход I2S2 DMA | `DMA1_Stream3_IRQn` | 0x0F | BSP `..._audio.c:970`, значение `..._audio.h:124` |
| USB OTG FS | `OTG_FS_IRQn` | 0,0 | `USB_DEVICE/Target/usbd_conf.c:94` |

Кнопка PA0 — `BUTTON_MODE_GPIO` (опрос), EXTI-прерывания нет.

### 3. Разделяемые структуры при вытеснении (по предложенной схеме, п. Этап 2)

| Структура | Производитель / Потребитель (контекст) | Вывод |
|---|---|---|
| Очередь кадров `fq` | ISR приёма (USART2/DMA, ур.2) пишет head+слот / `Lab_Process` (поток) читает | SPSC, данные пишутся до публикации head; аудио-выход(0) вытесняет обоих, но `fq` не трогает. **Безопасно** |
| Джиттер-буфер `jbuf` | `Lab_Process`(поток, `voice_sink`→`jb_push`) пишет head / аудио-выход ISR(0) читает и пишет tail | SPSC, потребитель(ISR) вытесняет производителя(поток) — видит старый head (меньше элементов), данные уже записаны. **Безопасно** |
| `playStereo`, буфер воспроизв. | только аудио-выход ISR(0) | не разделяется. **Безопасно** |
| `pdmBuf`/`pcmStereo`/`monoCap`, `acc16`/`accN`, `txSeq`/`txPayload`/`txEnc` | только аудио-вход ISR(2) (и его `tx_flush`) | аудио-выход(0) вытесняет, но не трогает. **Безопасно** |
| probe A (`aoX`) | только аудио-выход ISR(0) | **Безопасно** |
| probe B (`rxIsrX`) | только ISR приёма(2); чтение в потоке (диагностич.) | **Безопасно** |
| probe C (`loopMaxCyc`) | только `Lab_Process`(поток) | **Безопасно** |
| Консоль: `txRing` | только поток (запись и `tx_drain`) | **Безопасно** |
| Консоль: `rxRing` | USB ISR(3) пишет / поток читает | SPSC; другие ISR консоль не трогают. **Безопасно** |
| `dumpBuf`, статистика `rxDec` | ISR приёма(2) пишет / поток читает (диагностич., сброс — уже существующая безобидная гонка) | **Безопасно** |
| **`huart2`** (HAL UART) | RX — ISR приёма(2); TX — `HAL_UART_Transmit_IT` из аудио-входа ISR (на ПЕРЕДАТЧИКЕ) | Опасно ТОЛЬКО если аудио-вход вытесняет USART2 → **поэтому аудио-вход и USART2/DMA1_Stream5 на ОДНОМ уровне (2)** — взаимного вытеснения нет, реентерабельного доступа к `huart2` нет. **Безопасно при равном уровне** |
| `hi2s` (HAL I2S) | только аудио-выход ISR(0) в потоке (в `Audio_Init` — до включения вытеснения) | **Безопасно** |
| Флаги `g_*` (codec/rate/ptt/tone…) | поток пишет / ISR читают | одно слово, атомарно. **Безопасно** |

Небезопасных структур **не выявлено** — при двух обязательных условиях: (а) `USART2_IRQn` и
`DMA1_Stream5_IRQn` на одном уровне (приёмный колбэк не реентерабелен); (б) аудио-вход не выше
USART2 (иначе реентерабельный `huart2` на передатчике). Оба учтены в схеме.

### 4. Ловушки HAL (ожидания по тику в обработчиках выше SysTick)

Обработчики, которые окажутся **выше** SysTick(1) — только аудио-выход(0). Его путь:
`BSP_AUDIO_OUT_TransferComplete_CallBack` → `Audio_FillPlayback` (чистое чтение `jbuf`) →
`BSP_AUDIO_OUT_ChangeBuffer` (`..._audio.c:273`) → `HAL_I2S_Transmit_DMA` — по коду это только
`HAL_DMA_Start_IT` + включение I2S, **без `HAL_GetTick`/`HAL_Delay`/циклов ожидания**
(`stm32f4xx_hal_i2s.c`, тело функции проверено). probe A читает `HAL_GetTick()` — это чтение
переменной, не ожидание. → **зависаний нет**.

Аудио-вход(2) ниже SysTick(1) → `HAL_GetTick` во время него идёт. Его путь на передатчике:
`convert_block` → `BSP_AUDIO_IN_PDMToPCM` (чистая арифметика) → `Audio_OnCapture` → `tx_flush`
(FIR/кодек — арифметика) → `UartPort_SendRaw` → **`HAL_UART_Transmit_IT`** (`uart_port.c:347`) —
неблокирующе, без ожидания по тику. `HAL_Delay` в путях ISR не встречается; единственный
`HAL_Delay` — в `Console_Flush` (поток, в горячем пути LAB07 не вызывается). `cmd_send` крутит
`HAL_GetTick` в потоке — SysTick(1) вытесняет поток, значит цикл прогрессирует. → **ловушек нет**.

**Итог разведки: чисто, небезопасных структур нет.** Переход к Этапу 2.

## Этап 2 — правка

`configure_preemption()` (`speech.c:663`), вызывается в `Lab_Init` после `Audio_Init`
(`speech.c:704`) и повторно в `cmd_baud` после `UartPort_SetBaud` (`speech.c:427`, т.к.
`HAL_UART_MspInit` при реините возвращает `USART2_IRQn` в (0,0)). Выполняется с запретом
прерываний (`__disable_irq`/восстановление `PRIMASK`), чтобы смена группы и приоритетов была
атомарной.

### Приоритеты до/после (обоснование от списка п.2)

| Прерывание | ДО (GROUP_0, без вытеснения) | ПОСЛЕ (GROUP_4, preempt) | Почему |
|---|---|---|---|
| Аудио-выход `DMA1_Stream7` | 0x0E | **0** | должен прерывать приёмный ISR — это и есть лечение |
| SysTick | 0 | **1** | ниже выхода (не задерживает пере-взвод), выше остальных (HAL_GetTick идёт в USART/USB/аудио-входе) |
| Аудио-вход `DMA1_Stream3` | 0x0F | **2** | не выше USART2 → нет реентерабельного `huart2` на передатчике |
| USART2 | 0 | **2** | равен аудио-входу и своему RX DMA |
| USART2 RX `DMA1_Stream5` | 0 | **2** | равен USART2 — приёмный колбэк не реентерабелен |
| USB `OTG_FS` | 0 | **3** | ниже всех — не задерживает аудио (заодно снимает и возможные срывы от USB) |

Числа выбраны так, чтобы (1) аудио-выход прерывал всё, что раньше его блокировало; (2) SysTick
не мешал выходу, но обслуживал HAL_GetTick для нижних; (3) не возникло реентерабельности `huart2`
и приёмного колбэка (равные уровни там, где нужно). I2C кодека и прочие init-only прерывания не
трогались (в потоке данных не участвуют).

### Ожидаемый эффект

Когда 1-мс дедлайн пере-взвода приходится на длинный приёмный ISR, аудио-выход(0) теперь
**прерывает** его, пере-взводит DMA вовремя и возвращает управление. Длительность приёмного ISR
перестаёт влиять на пере-взвод → `probeA over` должен стать нулём.

## Откат (одним движением)

Убрать **оба** вызова `configure_preemption()` — в `Lab_Init` (`speech.c:704`) и в `cmd_baud`
(`speech.c:427`). Тогда останется `NVIC_PRIORITYGROUP_0` из `stm32f4xx_hal_msp.c:75` и приоритеты
из генерируемых MspInit — точное прежнее поведение. Вынос разбора из ISR (60dfbe6) при этом
сохраняется (он полезен сам по себе). Функцию `configure_preemption()` и прототип можно оставить
неиспользуемыми или удалить.

## Что НЕ трогалось

circular-режим аудио-выхода (запасной вариант, если этого мало), приоритеты в генерируемых
файлах и BSP, прикладная логика тракта, LAB04. probe A/B/C сохранены полностью.

## Процедура проверки (для владельца)

Прогон **не менее 9 минут** непрерывной передачи (ulaw, `rate 8000`, 460800), порядок как в
`REPORT_isr_deadline_probe.md`: `reset`, пустить передачу, слушать ≥9 минут (серии возвращались
~раз в 1.5 мин), между сериями опрашивать `voice`.
- Главный критерий: `probeA over` — **ноль** (при прежних 0.71/с за 9 мин ожидалось бы ~380);
- на слух прерываний нет ни в одной серии;
- `probeB rx-isr max` — примерно как было (~205 мкс), меняться не должен;
- `qover=0`, `under/lost/txdrop/fe/ore` нули; консоль/USB/приём не деградировали.
- LAB00 и LAB04 собираются (проверено) и должны работать как прежде (их NVIC не трогали).

Если `over` упал, но не до нуля — прислать числа (`over`, `probeA max`, привязку `first/last`),
посмотрим, что осталось (тогда следующий шаг — circular-DMA выхода).

**STOP** — прошивает и слушает владелец.
