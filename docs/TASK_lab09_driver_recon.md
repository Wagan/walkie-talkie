**Разведка Claude по открытым источникам (проверить, не принимать на веру):**

1. После покупки Decawave компанией Qorvo семейство DW3xxx довольно рано перешло с открытых

2. Последний выпуск — драйвер версии **06.00.14** из пакета для DWM3001CDK — поставляется
   **библиотекой без исходников и только под цели NRF**. Для нашего STM32F411 не годится.
3. Существует более ранний **открытый** выпуск: **DWS3000_Release_v1.1**, драйвер версии
   **04.00.00**. Он старее и хуже проверен, но с исходниками.
4. Сторонний проект на GitHub `br101/dw3000-decadriver-source` содержит исходную поставку
   `dwt_uwb_driver` версии **08.02.02** из пакета `DW3_QM33_SDK_1.0.2`, с правками под одну
   микросхему на плату. Код Qorvo там распространяется **по собственной лицензии Qorvo**
   (файл вида `LicenseRef-QORVO-2.txt`), а не под LGPL или MIT.
5. Порт под Zephyr `foldedtoad/dwm3000` следует релизу DWM3000 SDK V1.1 и заявляет
   работоспособность связки **Nucleo-F429ZI + DWS3000** — то есть исходники под STM32
   существуют и кем-то проверены.

**У владельца на диске** есть папка `QM33120WDK1` с документацией, но БЕЗ исходников:
`DW3QM33_SDK_Developer_Guide_0.1.1`, `DW3xxx_Driver_API_Guide_6.0.14`,
`DW3QM33_SDK_Release_Notes_0.1.1`, `UWB-Stack-R11.9.2`, плюс краткие руководства по
nRF52840 и QM33120WDK1. Версия 6.0.14 в руководстве по API соответствует именно бинарной
ветке — исходников там нет не потому, что они потерялись, а потому что их не поставляют.

## Важное ограничение, которое снимает один из вариантов

Владелец предположил, что можно взять чужие исходники, сделать глубокий рефакторинг и
положить результат в свой репозиторий. **Это не снимает лицензионных обязательств:**
переписанный код остаётся производной работой со всеми условиями исходной лицензии,
насколько бы сильно ни изменились имена и структура. Лицензионно чистых путей два —
соблюдать условия Qorvo как они есть, либо написать свой код по документации на регистры,
не заглядывая в их исходники.

Никто из нас не юрист, поэтому задача — **собрать факты, а не выносить правовую оценку**.

### Часть Б. Оценить объём и пригодность

- **Б1.** Размер открытого выпуска: сколько файлов и строк составляет собственно драйвер,
  отдельно от примеров и платформенной обвязки.
- **Б2.** Насколько платформенная часть завязана на Nucleo-F429ZI: что придётся заменить
  под нашу связку F411 + SPI4 + наши выводы. Ожидание — заменяется тонкий слой доступа к
  SPI и GPIO; проверить.
- **Б3.** Требования драйвера к окружению: нужна ли RTOS, динамическая память, конкретные
  версии HAL. Мы работаем без RTOS, в главном цикле, и это ограничение жёсткое.
- **Б4.** Оценка объёма кода и памяти: сколько примерно займёт во flash и RAM. У нас уже
  занято около 49 КБ flash из 512 КБ и около 13 КБ RAM из 128 КБ, запас есть, но цифру
  надо знать.

### Часть В. Альтернатива — свой драйвер по документации

## Дополнительные мелкие правки (сделать в этой же задаче)

1. **Конфигурация сборки `LAB09_DW1000`** — решение владельца принято. Завести по процедуре
   §5 хэндоффа: копия блока LAB09 с `LAB_ID=9`, добавленным символом `UWB_CHIP_DW1000` и
   своим `buildPath`. Резервная копия `.cproject` перед правкой, как обычно. Цель — чтобы
   сохраняемая ветвь DW1000 собиралась без правки исходников и не загнивала.
2. **Баннер при старте.** Каждая работа при запуске должна печатать свой номер работы и
   время сборки. Причина конкретная: владелец переключает работу через Run Configuration,
   забывая сменить активную конфигурацию сборки, и на плату уходит образ прошлой работы —
   это уже случилось и стоило часа разбирательств. Симптом коварный: консоль отвечает,
   команды есть, работает не та лаба. Реализовать так, чтобы номер брался из `LAB_ID`, а не
   вписывался руками. Затрагивает все работы — перечислить в отчёте, какие файлы изменены.
