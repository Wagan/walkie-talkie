## Задача B. Формат пакета

Пакет фиксированного размера, структура `__packed`, поля фиксированной ширины в порядке
от больших к меньшим — раскладка байт одинакова при любой оптимизации и без выравнивающих
дыр; проверяется `_Static_assert(sizeof == 14 + payload)`. Оба кита — один STM32F411
(little-endian), поэтому сырые байты структуры идут по проводу как есть.

| Поле | Тип | Назначение |
|---|---|---|
| `seq` | u32 | порядковый номер у отправителя (+1/пакет); по разрывам считаются потери |
| `t_tx` | u32 | метка времени отправителя (`HAL_GetTick`, мс) |
| `t_echo` | u32 | эхо последней принятой `t_tx` соседа → для RTT (0 если эха ещё нет) |
| `payload[N]` | байты | наполнитель фикс. размера (`LAB02_PAYLOAD_SIZE`, по умолч. 16) |
| `crc` | u16 | CRC-16/CCITT по всему пакету, КРОМЕ самого `crc` |

- **Размер вынесен константой** `LAB02_PAYLOAD_SIZE` (меняет размер пакета `LAB02_PACKET_SIZE`).
- **CRC**: CRC-16/CCITT (полином 0x1021, init 0xFFFF), табличная-независимая. Выбор объяснён
  в коде: несколько строк, но заметно надёжнее простой суммы/XOR — ловит все одиночные и
  двойные битовые ошибки и любые пакеты ошибок до 16 бит; на 115200 стоимость ничтожна.
  Простая сумма пропускала бы перестановки байт и часть искажений — для честной оценки мало.
- **Это ещё не протокол.** Кадрирования/поиска начала/ресинхронизации нет (это LAB03).
  Приём набирает ровно `LAB02_PACKET_SIZE` байт на пакет; выравнивание держится, пока не
  потерян байт (при потере — ошибки CRC, что и должно быть видно студенту).

## Задача C. Приём и передача

**Приём — по прерыванию USART1** (`HAL_UART_Receive_IT`), не по DMA. Обоснование (в коде):
в `.ioc` DMA для USART1 не сконфигурирован, а `.ioc` править нельзя; поднимать DMA целиком
в прикладном коде в обход CubeMX — хрупко. Приём по прерыванию неблокирующий, процессор не
ждёт, на 115200 и в нагрузке данные не теряет. Архитектура на callback'ах (RxCplt/Error) —
та же, что у DMA, поэтому в LAB04 (непрерывный аудиопоток) приём переведут на DMA circular
(включив его в CubeMX), не переписывая логику пакетов/ошибок.

- **USART1 global IRQ** в `.ioc`/NVIC включён не был — включаю в `Lab_Init`
  (`HAL_NVIC_SetPriority/EnableIRQ(USART1_IRQn)`), обработчик `USART1_IRQHandler` определён
  в самом файле (`HAL_UART_IRQHandler(&huart1)`).
- **Передача неблокирующая** — `HAL_UART_Transmit_IT`; флаг `txBusy` снимается в `TxCplt`.
- **Печать из ISR — нигде** (правило C3): в callback'ах только счётчики (volatile) и
  светодиоды; вся печать — в `Lab_Process`.
- **Ошибки приёмника считаются по видам** (в `HAL_UART_ErrorCallback` по `huart->ErrorCode`):
  переполнение `ORE`, ошибка кадра `FE`, ошибка чётности `PE`, ошибка шума `NE` — каждый в
  своём счётчике; после ошибки приём перезапускается. Так студент видит, что именно
  происходит при завышенной скорости.

## Задача D. Режимы работы

Режим выбирается константой `LAB02_MODE` (ввода команд пока нет — это LAB05).

**1. Периодический (`PERIODIC`, по умолчанию):** пакет раз в `LAB02_TX_INTERVAL_MS`
(100 мс), раз в секунду печать статистики:
`tx, rx, lost (разрывы seq), crc (ошибки CRC), ore/fe/pe/ne (ошибки приёмника по видам),
rtt (последняя round-trip, мс)`.

**2. Нагрузочный (`LOAD`):** пакеты подряд без пауз в течение `LAB02_LOAD_MS`, конвейер
гонится в `TxCplt` (чтобы линия была насыщена). По окончании — печать:
`elapsed, tx_bytes, rx_bytes, rate (B/s и bit/s), lost, crc_err`, и последняя RTT.

**Что измеряется и что ограничивает скорость** (комментарий в коде): скорость считается по
принятым байтам за окно (`rx_bytes/elapsed`). На 115200 8N1 предел линии =
`115200/10 = 11520 байт/с` (10 бит на байт со старт/стоп). Обработка приёма (~11.5 тыс.
IRQ/с) и CRC на ядре 96 МГц ничтожны, а печать идёт ПОСЛЕ окна измерения — поэтому число
отражает КАНАЛ (провод+UART), а не диагностику. При повышении скорости первым проявится
переполнение приёмника (`ORE`).

**RTT (для LAB10):** каждый пакет несёт `t_echo` — отражённую метку `t_tx` соседа. Когда
наша метка возвращается, `RTT = now − t_echo`. Часы плат не синхронизированы, поэтому меряем
именно round-trip, а не одностороннюю задержку.

## Задача E. Индикация (по аналогии с LAB00)

- **LED3 (оранжевый)** — переключается на каждый ОТПРАВЛЕННЫЙ пакет.
- **LED4 (зелёный)** — переключается на каждый КОРРЕКТНО принятый пакет (CRC сошлась).
- **LED5 (красный)** — загорается на ЛЮБОЙ ошибке (неверная CRC или ошибка приёмника).

Так без отладчика видно: мигают оба (оранж+зел) — обмен идёт; горит красный — есть ошибки.

## Порядок проверки для владельца

**Соединение (три провода, крест-накрест + земля):**
- `кит1 PA9 (TX, разъём P2 к.44)` → `кит2 PA10 (RX, P2 к.41)`
- `кит2 PA9 (TX, P2 к.44)` → `кит1 PA10 (RX, P2 к.41)`
- `кит1 GND ↔ кит2 GND` — земля на разъёме **P1** (к.1/2/5/23/49/50). Земля уже общая через
  USB-хаб, но явный провод GND↔GND нужен.

**Что залить:** сделать активной конфигурацию **LAB02** (Project → Build Configurations →
Set Active → LAB02), собрать, прошить ОБЕ платы одной прошивкой.

**Что должно появиться в консоли (SWV ITM Data Console, порт 0) на КАЖДОЙ плате:**
- при старте: `[I] LAB02 uart link: 115200 8N1, packet=30 B (payload 16), mode=PERIODIC`;
- раз в секунду: `[I] stat: tx=… rx=… lost=0 crc=0 ore=0 fe=0 pe=0 ne=0 rtt=… ms`.

**Успех:** на обеих платах `rx` растёт вместе с `tx`, `lost=crc=ore=fe=pe=ne=0`, `rtt`
несколько мс; мигают LED3 (оранж) и LED4 (зел), LED5 (кр) не горит.

**Типичные неисправности:**
- **Провод не подключён / нет питания у второй платы:** `tx` растёт, `rx=0`, зелёный не
  мигает. Приёмных пакетов нет.
- **Перепутаны TX и RX** (TX↔TX, RX↔RX): `rx=0` (данные не приходят); либо мусор → всплеск
  `crc` и, возможно, `fe`/`ore`, горит красный.
- **Нет общей земли:** приём нестабилен — растут `crc`, `fe`, `ore` (ошибки кадра/шум/
  переполнение), красный горит; `rx` заметно меньше `tx`.
- **Скорость поднята слишком высоко** (в опытах): первым растёт `ore` (переполнение), за ним
  `crc` из-за сбоя выравнивания.
