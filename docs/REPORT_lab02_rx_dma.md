# Отчёт: TASK_lab02_rx_dma — перевод приёма LAB02 на кольцевой DMA + IDLE

Коммит с изменениями: `__HASH__`.

Перевод приёма LAB02 с «приёма на пакет» (`HAL_UART_Receive_IT`) на непрерывный приём по
DMA в кольцевой буфер с событием простоя линии (`HAL_UARTEx_ReceiveToIdle_DMA`), по эталону
ST `UART_ReceptionToIdle_CircularDMA`. Причина перехода установлена в
`TASK_uart_rx_reference` (см. `docs/REPORT_uart_rx_reference.md`): не настройки UART и не
обработка ошибок, а пакетная рассинхронизация приёма фиксированной длины.

Все правки — только в `App/Labs/uart_link.c` и документации. `.ioc`, HAL, CMSIS, BSP,
ThirdParty и сгенерированные обработчики прерываний не трогались. LAB00 не затронут.

## Что изменено

1. **Убран собственный `USART1_IRQHandler`** и ручное `HAL_NVIC_SetPriority/EnableIRQ(USART1_IRQn)`
   из `Lab_Init`. Это устраняет ошибку сборки `multiple definition of USART1_IRQHandler`:
   после включения прерывания USART1 в `.ioc` CubeMX генерирует свой обработчик в
   `Core/Src/stm32f4xx_it.c:231` (проверено), плюс `DMA2_Stream2_IRQHandler` (`:245`).
   Наш файл теперь этих векторов не определяет и NVIC руками не включает.
2. **Приём запускается один раз** в `Lab_Init` через `lab02_start_rx()` →
   `HAL_UARTEx_ReceiveToIdle_DMA(&huart1, rxRing, LAB02_RX_RING_SIZE)`. Режим DMA — circular
   (задан в `.ioc`/msp: `hdma_usart1_rx` = DMA2 Stream2, канал 4, `DMA_CIRCULAR`, байт,
   инкремент по памяти, FIFO off — `Core/Src/stm32f4xx_hal_msp.c:115-130`), поэтому приём
   бесконечный, перезапрос буфера не нужен.
3. **Разбор входящего потока — в `HAL_UARTEx_RxEventCallback`** (архитектура эталона): хранит
   позицию последнего разобранного байта `rxOldPos`, забирает новый участок кольца
   `[rxOldPos, Size)` с корректной обработкой заворота (двумя сегментами: «хвост» до конца
   кольца + «голова» с начала). Из колбэка ничего не печатается — только разбор и счётчики.
4. **Сборка пакетов из потока** (`lab02_feed_byte`) с минимальной ресинхронизацией по CRC.
5. **Статистика дополнена счётчиком `resync`** (и в PERIODIC, и в LOAD).
6. **Устранены предупреждения** (`loadStartMs`/`loadDone` вынесены под `#if LOAD`).

## Устройство приёма (три события одинаково корректны)

`HAL_UARTEx_RxEventCallback(huart, Size)` вызывается на трёх событиях; `Size` — **абсолютная**
позиция в кольце, до которой данные готовы (проверено по HAL):
- **Half-Transfer (HT):** `Size = RxXferSize/2` = 128 (`stm32f4xx_hal_uart.c:3121`);
- **Transfer-Complete (TC):** `Size = RxXferSize` = 256 (`:3082`);
- **IDLE (простой линии):** текущая позиция по `NDTR` (`:2479-2510`).

Обработка одинаковая: скармливаем сборщику все новые байты `[rxOldPos, Size)`. Заворот кольца
(`Size < rxOldPos`) обрабатывается двумя циклами. Случай `Size == 256` (TC) попадает в ветку
`Size > rxOldPos` и обрабатывается штатно, бесконечного цикла нет (следующее событие всегда
даёт `Size < 256`). Пакет, «разорванный» границей HT/TC, не теряется: HT/TC **не** считаются
границей кадра, частично собранный пакет сохраняется и достраивается на следующем событии.

## Сборка пакетов и ресинхронизация

Передатчик шлёт пакеты фиксированной длины (30 байт = 14 служебных + payload 16). Из
непрерывного потока их надо выделить:

- **Основная точка синхронизации — IDLE.** В режиме PERIODIC между пакетами есть пауза, и
  событие IDLE совпадает с границей пакета. Если в момент IDLE в сборщике остался НЕполный
  пакет (значит, внутри кадра потерян байт) — сбрасываем остаток, чтобы следующий пакет начать
  с нуля. Это самый надёжный ресинк.
- **Резерв на случай отсутствия пауз (LOAD) — сдвиговая ресинхронизация по CRC.** Как только
  собран полный пакет — проверяется CRC. Не сошлась → выбрасываем самый старый байт, сдвигаем
  буфер на один (`memmove`), длина = `PACKET_SIZE-1`, ждём следующий байт. За один входящий
  байт — ровно один сдвиг (работа O(1) на байт). Число попыток естественно ограничено:
  приёмник дошагает до истинной границы не позже, чем за `PACKET_SIZE` байт, после чего CRC
  сойдётся и синхронизация восстановится. Полное кадрирование с маркерами/экранированием —
  содержание LAB03.
- **Счётчик `resync`** считает ЭПИЗОДЫ потери синхронизации (переход «был синхронизирован →
  сбой»), а не каждый сдвиг — это и есть полезная для студента мера устойчивости канала.
  `crc` по-прежнему считает все неудачные проверки CRC.

## Размер кольцевого буфера — 256 байт, обоснование

Буфер должен с запасом вмещать несколько пакетов, чтобы DMA не «догнал» разбор. Пакет = 30
байт, берём **256 байт (~8 пакетов)**:
- на 115200 8N1 линия даёт 11520 байт/с (10 бит/байт); половина кольца (128 байт) при самом
  плотном (нагрузочном) потоке набегает за ~11 мс, а её разбор в колбэке — десятки микросекунд
  (CRC на ядре 96 МГц). DMA физически не может обогнать разбор → переполнения кольца нет;
- в PERIODIC между пакетами пауза, колбэк приходит по IDLE ровно на границе пакета, кольцо
  почти всегда пустое — запас тем более избыточный;
- степень двойки удобна и оставляет резерв на будущее увеличение payload.

## Поведение при ошибках в DMA-режиме (проверено по коду HAL)

В DMA-режиме обработка ошибок **отличается** от режима прерываний. В `HAL_UART_IRQHandler`
при активном DMA (`DMAR` установлен) **любая** ошибка приёмника — FE/NE/PE/ORE — считается
блокирующей: вызывается `UART_EndRxTransfer` (RxState→READY, прерывания приёма выключаются) и
DMA-приём прерывается через `HAL_DMA_Abort_IT`, после чего вызывается `HAL_UART_ErrorCallback`
(`stm32f4xx_hal_uart.c:2410-2416, 2424-2445`). Ошибка самого контроллера DMA приводит к
`UART_DMAError` — тот же `UART_EndRxTransfer` + `HAL_UART_ErrorCallback` (`:3156-3171`). Итог:
**в DMA-режиме на любой ошибке приём ОСТАНАВЛИВАЕТСЯ, и его надо перезапускать.** Поэтому в
`HAL_UART_ErrorCallback` мы считаем счётчики ошибок и вызываем `lab02_start_rx()`, который
заново запускает `HAL_UARTEx_ReceiveToIdle_DMA` и сбрасывает разбор (`rxOldPos=0`, `asmLen=0`),
т.к. после перезапуска DMA пишет с начала кольца. Этот вывод записан комментарием в коде.

## Что стало со статистикой

- **PERIODIC:** строка `stat:` дополнена полем `resync=`. Остальные поля (`tx/rx/lost/crc/
  ore/fe/pe/ne/rtt`) сохранены.
- **LOAD:** строка `load done:` дополнена `resync=`. Скорость по-прежнему считается по
  фактически принятым байтам `bytesRx` — теперь он растёт в `RxEventCallback` на каждый
  доставленный DMA байт (независимо от кадрирования), что корректно отражает пропускную
  способность КАНАЛА. Измерение печатается ПОСЛЕ окна, разбор в колбэке ничтожен по времени —
  число отражает провод, а не диагностику.

## Что проверить владельцу и как выглядит успех

Собрать конфигурацию **LAB02** (LAB_ID=2), прошить оба кита, соединить крест-накрест PA9↔PA10
+ общая земля (или замкнуть PA9↔PA10 на одной плате для теста).

- **PERIODIC (по умолчанию):** в SWV раз в секунду строка `stat: ... rx=... crc=... resync=...`.
  Успех: **`rx` монотонно растёт** (примерно как `tx` встречного кита), зелёный LED4 мигает,
  `crc` и `resync` близки к нулю или не растут. Ранее было `rx=0` — теперь должно быть
  ненулевым; это и есть подтверждение, что рассинхронизация устранена.
- **LOAD** (`LAB02_MODE` → `LAB02_MODE_LOAD`): по истечении `LAB02_LOAD_MS` одна строка
  `load done: ... rate=... B/s ... resync=...`. Успех: `rate` близка к пределу линии (~11520
  байт/с при 115200), `resync` небольшой.
- Единичные `fe`/`crc`/`resync` при этом допустимы (реальный канал), важно, что приёмник
  **восстанавливается** и `rx` продолжает расти, а не залипает на нуле.

## Ограничения / открытое

- Полноценное кадрирование (маркеры, экранирование, длина в заголовке) — LAB03; здесь только
  ресинхронизация по CRC + IDLE.
- TX остался на `HAL_UART_Transmit_IT` (по прерыванию) — задача касалась только приёма. Перевод
  TX на DMA (DMA2 Stream7 ch4) при желании — отдельный шаг, для LAB02 не требуется.
