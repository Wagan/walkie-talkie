# Отчёт: TASK_lab04_voice_wire — речь по проводу (полудуплекс PTT)

Коммит с изменениями: `b3ac476`.

LAB04 — речь по проводу: PCM с микрофона одной платы идёт SLIP-кадрами по USART2 на вторую и
воспроизводится на её кодеке. Режим — полудуплекс с PTT (кнопка PA0). Сборка проверена локально:
все конфигурации LAB00/02/03/04/05 — 0 ошибок, 0 предупреждений.

Правки: `App/Common/audio.{h,c}` (новый общий аудиотракт), `App/Labs/stand_check.c` (LAB00 →
тонкий адаптер), `App/Labs/voice_wire.c` (LAB04), `App/Common/uart_port.{h,c}` (сырой кадровый
TX + перехват RX), `App/Common/frame.h` (предел кадра 256), `lab.h`, `.cproject` (конфигурация
LAB04), консоль/CDC-хук расширены на LAB04. `.ioc`, HAL, CMSIS, BSP, ThirdParty не трогались.

## Задача A. Аудиотракт как общий модуль

Тракт звука вынесен в `App/Common/audio.c` (guard `LAB_ID==0||4`) без изменения данных: приём
микрофона кольцевым DMA (I2S2) → `BSP_AUDIO_IN_PDMToPCM` → выход на кодек (I2S3, DMA NORMAL со
сменой буфера в колбэке). Модуль владеет всеми колбэками BSP и даёт **независимые** направления
через слабые хуки (по 1 мс = 16 отсчётов):
- `Audio_OnCapture(mono, 16)` — свежий моно-блок с микрофона (левый канал: микрофон один);
- `Audio_FillPlayback(mono, 16)` — запросить следующий блок на воспроизведение (по умолчанию тишина);
- `Audio_OnError(who)`.

Независимость направлений и нужна для полудуплекса: в каждый момент активно одно.

**LAB00 переписана в тонкий адаптер** (`stand_check.c`): хуки реализуют петлю микрофон→кодек через
двойной буфер, те же светодиоды (LED4 init, LED6 обработка, LED5 ошибка), тот же статус и SWO
heartbeat. Поведение (звук, LED, вывод) сохранено — петля даёт тот же результат (моно левый канал
дублируется в оба на выходе, для моно-источника это идентично).

## Задача B. Передача речи

- Моно-блоки 1 мс накапливаются в кадр **5 мс = 80 отсчётов (160 байт PCM)** и упаковываются в
  SLIP-кадр `frame.c`. Полезная нагрузка = `seq(u16) + 80×int16` = 162 байта.
- **Выбор 5 мс** — баланс: меньше блок → относительно больше накладных (на кадр фиксированно
  2 END + 2 CRC + 2 seq = 6 байт); больше → выше задержка. При 5 мс накладные ≈ 6/160 = 3.75 %
  плюс стаффинг; задержка накопления 5 мс.
- **Передача не блокирует запись:** отправка неблокирующая (`UartPort_SendRaw` → `Transmit_IT`);
  если линия занята — кадр **отбрасывается** (`txdrop`), а не копится. Для речи задержка важнее
  полноты (устаревший звук бесполезен). `seq` при этом всё равно инкрементируется, чтобы приёмник
  увидел потерю.
- **Худший случай стаффинга:** если каждый байт PCM окажется маркером END/ESC — кодирование
  удваивает содержимое (2× по 164 байта ≈ 328 байт на кадр). На практике для речи доля таких
  байт ≈ 2/256 ≈ 0.8 %. Даже удвоение укладывается: 5 мс·2×160 байт·10 бит/(5 мс) ≈ 640 кбит/с
  < 737 кбит/с при 921600; средний поток ≈ 335 кбит/с (запас ~2.2×).

## Задача C. Приём и воспроизведение

- Принятые байты перехватываются `UartPort_SetRxTap` и идут в собственный `Frame_Decoder` LAB04;
  корректный кадр распаковывается в отсчёты и кладётся в джиттер-буфер.
- **Джиттер-буфер** — кольцо отсчётов `2048 (128 мс)`, SPSC (приёмный ISR двигает head, кодечный
  ISR — tail). Старт воспроизведения — при заполнении **20 мс** (prefill), чтобы сгладить
  неравномерность приёма и расхождение тактовых источников двух плат (каждая на своём PLLI2S).
  - **Опустошение (under):** отсчётов не хватает → маскировка провала линейным затуханием
    последнего блока к нулю (без щелчка), далее тишина; воспроизведение ждёт повторного prefill.
  - **Переполнение (over):** буфер полон → входящие отсчёты отбрасываются (tail из чужого ISR не
    двигаем — сохраняем SPSC-безопасность).
- **Потеря кадра** (разрыв `seq`) → в буфер вставляется тишина на длину потерянных кадров
  (timeline не сбивается, нет рассинхронизации), считается `lost`. Большой разрыв (>8 кадров) не
  заполняется — трактуется как ресинхронизация.
- Пока PTT нажата — воспроизведение выключено (тишина), входящие кадры не буферизуются.

## Задача D. Управление и диагностика

- **PTT** по кнопке PA0 (`BSP_PB`), подавление дребезга: смена состояния принимается только после
  стабильности ≥ 20 мс. Эффективный PTT = кнопка **ИЛИ** команда `ptt on`.
- **Светодиоды:** LED3 — передача (PTT), LED4 — активность приёма (переключается на каждый принятый
  кадр), LED5 — ошибка аудиотракта, LED6 — USB «жив» (~2 Гц).
- **Консоль** (общая, как в LAB03/LAB05): базовые `help/send/sendbyte/stat/reset/dump/regs/baud`,
  плюс:
  - **`voice`** — статистика речевого тракта и оценка задержки;
  - **`ptt on|off`** — передача командой без кнопки (отладка в одиночку);
  - **`tone on|off`** — вместо микрофона передавать **тон 1 кГц** (16-точечная синус-таблица при
    16 кГц = ровно 1000 Гц). Главный инструмент: объективная проверка тракта без разговора —
    чистый тон на приёме означает, что тракт цел; искажения/разрывы слышны сразу.

## Задача E. Измерение задержки

Честно: акустическую задержку «микрофон→динамик» **без осциллографа измерить нельзя** — нет
общего момента отсчёта между звуком в микрофоне и звуком из динамика. Реализована **расчётная
оценка** (в выводе `voice`): односторонняя задержка ≈ накопление кадра (5 мс) + prefill
джиттер-буфера (20 мс) + буфер кодека (~2 мс) ≈ **27 мс** (плюс время кадра на линии ~4 мс,
конвейеризовано). Для LAB10 этого достаточно как сравнимая метрика между каналами.

Способ реального измерения (когда будет осциллограф, для LAB10): на передающей плате дёргать
свободный GPIO в момент генерации маркерного отсчёта тона, на приёмной — в момент его
воспроизведения; осциллограф между двумя GPIO двух плат показывает сквозную задержку. На одной
плате так не измерить — полудуплекс не даёт одновременно передавать и воспроизводить.

## Как это не ломает пройденные работы

- `audio.c` (guard 0||4): для LAB00 даёт тот же тракт; LAB02/03/05 его не линкуют.
- `uart_port` расширен (SendRaw/RxTap) аддитивно; при `g_rxTap==NULL` (LAB02/03/05) поведение
  прежнее. `frame.h` предел 64→256 — тестовые кадры LAB03 (30 Б) укладываются, поведение то же.
- Консоль/CDC-хук расширены с `3||5` на `3||4||5` — на LAB03/LAB05 не влияет.
- Сборка всех конфигураций — 0 ошибок, 0 предупреждений (проверено локально headless-сборкой).

## Порядок проверки для владельца

1. Собрать конфигурацию **LAB04**, прошить **обе** платы. Соединить USART2 крест-накрест
   (кит1 PA2→кит2 PA3, кит2 PA2→кит1 PA3, общая земля P1). Наушники в джек приёмной платы.
   Убедиться, что USART2 = 921600 (в .ioc).
2. К обеим платам подключить USB-консоль (или хотя бы к передающей).
3. **Тон:** на передающей `tone on`, зажать **PA0** (или `ptt on`). На приёмной должен звучать
   **чистый 1 кГц**; LED3 на передающей и LED4 на приёмной активны. Отпустить PA0 — тишина.
4. **Голос:** `tone off`, зажать PA0 и говорить в микрофон передающей платы — на приёмной слышен
   голос. Отпустить — приём/тишина.
5. В консоли `voice` — смотреть `sent/recv/lost/txdrop/under/over` и `jb_fill`. В норме `lost` и
   `txdrop` малы, `jb_fill` держится около prefill.
6. Двусторонность: то же в обратную сторону (роли PTT меняются) — классический полудуплекс рации.

**Проверено на железе** (см. PROJECT_HANDOFF §6): речь по проводу, полудуплекс/PTT и джиттер-буфер
работают; рабочая скорость **460800** (на 921600 линия сыплется — свойство скорости). Позже к LAB04
добавлено вытеснение прерываний (лечение коротких провалов звука, `REPORT_preemption_other_labs.md`).
