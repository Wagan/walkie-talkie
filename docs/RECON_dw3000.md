## ФАКТЫ А — SPI-транзакция

- **А1. Формат чтения одного регистра.** Заголовок — **1 или 2 октета** ([UM] §2.3.1.2, стр.11:
  *«Each SPI transaction starts with a one or two octet transaction header…»*). Первый бит —
  направление: **0 = read**, 1 = write ([UM] §2.3.1.2, стр.11). Короткий адрес (1 октет): bit0=RD/WR,
  bit1=0 (признак 1-октетного заголовка), биты [5:1] = 5-битный базовый адрес регистрового файла;
  для DEV_ID (файл 0x00) заголовок = **один октет `0x00`** ([UM] §2.3.1.2.2 / Figure 4, стр.13–14).
  Полный адрес (2 октета) — для доступа к суб-адресу. **Есть завершающий (padding) бит** в конце
  заголовка: *«This command structure is padded by a trailing bit to allow the SPI address decoder
  time to fetch any read data»* ([DS] §1.3.3, стр.7) — даёт декодеру время подготовить данные чтения.
- **А2. Порядок байт данных — младшим октетом вперёд (LSB first).** [UM] §8, стр.72: *«the octets are
  output least significant octet first»*; [DS] §1.3, стр.5: *«all data is transmitted commencing with
  lowest addressed byte»*. (Совпадает с DW1000 — но проверено по документу, не принято на веру.)
- **А3. Порядок бит — MSB first; CSn низкий всю транзакцию.** [UM] §2.3.1.2, стр.11: *«…high-order bit
  sent first in time (MSB first)»*. [DS] §1.3, стр.5: *«Assertion low of SPICSn initializes transaction.
  De-assertion high of SPICSn ends the SPI transaction.»* Плюс [DS] §1.3, стр.5: SPIMISO уходит в
  open-drain при снятом SPICSn.
- **А4. Потолок SPICLK зависит от состояния (иначе, чем 3 МГц у DW1000).** Сразу после сброса в
  **INIT_RC SPI ограничен 7 МГц** ([UM] §2.4 Table 4, стр.19: *«…but limited to 7 MHz…»*). В **IDLE_RC**
  — полноскоростной SPI (ядро ~120 МГц). Максимум **38 МГц — только в IDLE_PLL** ([UM] Table 4, стр.19:
  *«…up to 38 MHz, the maximum SPICLK frequency»*), при условии «SPI mode 0» ([DS] Table 1, t10, стр.5).

## ФАКТЫ Б — идентификатор устройства

- **Б1. Адрес `0x00:00`, 4 октета, RO. Значение = `0xDECA0302` (non-PDoA) или `0xDECA0312` (PDoA).**
  [UM] §8.2.2.1, стр.74: *«For the production DW3000 the Device ID is set to 0xDECA0312 or 0xDECA0302»*;
  RIDTAG[31:16]=0xDECA, MODEL[15:8]=**0x03** (*«The DW3000 is device type 0x03»*). [UM] §1.1, стр.7:
  *«…0xDECA0302 and 0xDECA0312, the non-PDoA and PDoA device respectively»*. Привязку именно `DW3110` к
  одному из двух значений документы не дают — см. НЕ УСТАНОВЛЕНО.
- **Б2. Несуществующий/зарезервированный адрес → `0xDEADDEAD` (маркер сохранён).** [UM] §8, стр.72:
  *«unused or reserved registers return 0xDEADDEAD when read»*. Диагностический маркер тот же, что у DW1000.
- **Б3. До первого чтения DEV_ID спец-записи не нужно.** Регистр «hard-coded into the silicon», RO
  ([UM] §8.2.2.1, стр.74) — читается, как только чип отвечает по SPI (после снятия сброса и входа в
  INIT_RC→IDLE_RC; SPI-доступ появляется после ~70 µs OTP boot, [UM] Figure 8 / [DS] Figure 1).

## ФАКТЫ В — сброс и включение

- **В1. RSTn — активно-низкий, только open-drain, высоким извне не подавать.** [DS] Table 2, стр.12:
  *«RSTn … Active Low Output. May be pulled low by external open drain driver to reset the DW3000»*;
  тип O-H = *«Defaults to output, high level after reset»* ([DS] Table 3, стр.12). То есть требование
  такое же, как у DW1000. **Минимальная длительность низкого импульса числом в этих двух документах не
  задана** (см. НЕ УСТАНОВЛЕНО).
- **В2. Тайминги POR (холодный старт).** FAST_RC и XTAL стартуют «within 500 µs and 1 ms respectively»
  ([UM] §2.5, стр.21); цифровое ядро выходит в **INIT_RC**, далее ~**70 µs OTP boot** → появляется
  хостовое прерывание и разрешается SPI ([UM] Figure 8, стр.21; [DS] Figure 1, стр.4). Затем **IDLE_RC**;
  хост ставит бит AINIT2IDLE (SEQ_CTRL) → включается CLKPLL → **IDLE_PLL**. Тёплый старт из сна:
  ~85 µs AON+OTP boot, ~1 ms AON wake-up ([UM] Figure 9, стр.23). Ориентир: после снятия RSTn выждать
  порядка «~1 мс (XTAL) + ~70 µs (OTP)» до валидного ответа SPI.
- **В3. Режим SPI защёлкивается по GPIO5/GPIO6 при включении; по умолчанию — mode 0.** [DS] Figure 1
  (POR), стр.4: *«Sample GPIOs 5&6 to set SPI mode»*. GPIO5 = SPIPOL, GPIO6 = SPIPHA ([DS] Table 2,
  стр.11–12), после включения обе возвращаются к GPIO. Внутренние подтяжки по умолчанию **вниз** (кроме
  SPICSn — вверх): [DS] §6.3, стр.26 — *«…defaults to enabled and pull-down except for the SPICSn pin»*.
  Значит **неподключённые GPIO5/GPIO6 → SPIPOL=0, SPIPHA=0 → SPI mode 0** (совпадает с t10 «SPI mode 0»).

## ФАКТЫ Г — подключение шилда к киту

**Г1. Таблица «сигнал → вывод шилда (Arduino) → вывод кита».** Сторона шилда — [QSG] Table 1, стр.3
(коннекторы CON1–CON4; текстовых меток «D13…» в таблице нет, они выведены по стандарту Arduino R3).
Сторона кита — `docs/PINOUT_dwm1000_lab09.md` (раскладка железом уже подтверждена на DW1000, не меняется):

| Сигнал | Вывод шилда (Arduino R3) | Разъём шилда | Вывод кита | Разъём кита |
|---|---|---|---|---|
| SPI SCK | D13 | CON1 | PE12 (SPI4_SCK AF5) | P1 к.30 |
| SPI MISO | D12 | CON1 | PE13 (SPI4_MISO AF5) | P1 к.31 |
| SPI MOSI | D11 | CON1 | PE14 (SPI4_MOSI AF5) | P1 к.32 |
| SPI CSn/SS | D10 | CON1 | PE11 (GPIO выход) | P1 к.29 |
| IRQ | D8 | CON1 | PE9 (GPIO вход) | P1 к.27 |
| **RSTn** | **D7** | **CON4** | PE10 (GPIO open-drain) | P1 к.28 |
| 3V3 | 3V3 | CON2 | 3 В кита | P2 к.5 или к.6 |
| GND | GND (×2) | CON2 | общая земля | P1 к.1/2/5/23/49/50 |

Шесть нужных линий — те же, что для DW1000, раскладка кита **не меняется** (STOP не сработал). Тонкость:
у шилда **RSTn выведен на D7 (CON4)**, а не рядом с SPI на CON1 — учесть при разводке жгута.

**Г2. Джампер J1 — источник питания модуля.** [QSG] §4.1, стр.7: *«"Up", pin 2 and 3 shorted → 3V3 pin
from the Arduino connector; "Down", pin 1 and 2 shorted → 3V3 DC/DC on the DWM3000EVB»*. Центральный
вывод (pin 2) — вход питания модуля. **Обоснование решения владельца перейти на питание с
Arduino-разъёма (положение «Up»):**
- обе позиции подают на модуль **номинально 3.3 В** (в самих названиях — «3V3 pin» и «3V3 DC/DC»); 5 В на
  VDD модуля через J1 **не заводится** — согласуется с пределами [DS] Table 4 (VDD3V3 2.5…3.6 В) и Table 9
  (Abs Max 4.0 В). Значит переход на «Up» безопасен по уровню;
- «Up» проще: раз все шесть линий и так идут через Arduino-разъём, питание берётся оттуда же (один жгут,
  одна земля) — это в пользу решения владельца;
- **чем питается ВХОД собственного DC-DC (5 В или 3.3 В) — в документах НЕ указано** (нужна схема платы,
  её в наборе нет). Поэтому оспорить/подтвердить «заработает ли в положении Down без подачи 5 В» по
  документам нельзя. Практический вывод: **положение «Up» (3V3 с Arduino) — определённое и безопасное**,
  кит должен выдать на 3V3-пин шилда честные 3.3 В.

**Г3. Что кит подаёт на шилд.** Достаточно **3.3 В** (на 3V3-пин CON2) + GND. 5 В модулю не нужно
(в положении «Up»). Ток для оценки нагрузки линии 3.3 В: [DS] Table 5, стр.13 — RX ≈ 50–55 мА,
TX ≈ 40–45 мА (каналы 5/9). 3 В кита (P2 к.5/6) должно потянуть; при просадке — внешние 3.3 В с общей
землёй (та же оговорка, что была для DWM1000).

**Г4. Притяжка IRQ вниз.** Рекомендует [DS] Table 2, стр.11 (*«…may cause spurious interrupts unless
pulled low externally (100 k recommended)»*) и [DS] Figure 11, стр.20 (*«Optional pulldown on IRQ… 100 k»*)
— **для режимов SLEEP/DEEPSLEEP**. На первом шаге LAB09 (живость + ID, сон не используется, IRQ по
опросу не читаем) притяжка **не обязательна**; понадобится, когда включим прерывания/сон.

**Г5. Инженерные образцы — проверить наклейку.** [QSG] §5 Table 4, стр.8: серийные промаркированы
**`DWM3000`**; инженерные — с суффиксом **`.E1.0`** (PCB v1.3) или **`.E1.1`** (PCB v1.4). У **ES1.0
(`.E1.0`) GPIO5 и GPIO6 переставлены** (*«GPIO5 and GPIO6 swapped»*), а именно эти выводы при старте
задают SPIPOL/SPIPHA. **Чем грозит:** на ES1.0 при внешней подтяжке GPIO5/6 защёлкнется не тот SPI-режим
(перепутаны CPOL/CPHA). Мы GPIO5/6 не подключаем (mode 0 по внутренним подтяжкам) — риск ниже, но
владельцу нужно **прочитать на наклейке модуля**: если стоит `.E1.0` — учитывать перестановку; серийный
`DWM3000` или `.E1.1` — без этой проблемы. (У ES1.0/ES1.1 ещё не распаяны 100 нФ VDD-конденсаторы.)

## ФАКТЫ Д — что меняется в архитектуре LAB09

**Д1. Скорости, каналы, преамбула.** Только **два data rate: 850 kb/s и 6.8 Mb/s** (110 kb/s удалён,
[UM] §2.2, стр.10). Только **каналы 5 (6489.6 МГц) и 9 (7987.2 МГц)**, BW 499.2 МГц ([UM] §1.1 стр.7,
Table 8 стр.28). PRF 16/64 МГц, коды преамбулы 3–4 (16 МГц) / 9–12 (64 МГц); длина преамбулы 64…4096
символов ([UM] Table 10, стр.32). **Числового размена «медленнее → чувствительнее (дБм)» в документах
НЕТ** — только качественное *«communication range is dependent on data rate and preamble length»*
([UM] §11, стр.246); [DS] Table 6 (стр.14) даёт лишь CF и BW, без чувствительности по data rate. Значит
демонстрировать студенту «медленнее — дальше» на DW3000 можно лишь качественно (850 kb/s + длинная
преамбула против 6.8 Mb/s), без паспортных дБм.

**Д2. Длина кадра.** Стандартный IEEE 802.15.4 — **до 127 байт** ([UM] §2.10, стр.31); расширенный режим
— **до 1023 байт** (PHR_MODE в 0x00:10), но он несовместим с 802.15.4 и требует одинаковой настройки на
обоих концах. **Голосовой кадр Codec2 (несколько десятков байт) свободно влезает в стандартные 127 байт**
— расширенный режим не нужен.

**Д3. Драйвер производителя.** Существует как исходники: *«Decawave also provides DW3000 device driver
software as source code… API functions to initialise, configure and control the DW3000… for ARM
Cortex-M… simple examples… two-way ranging»* ([UM] §1.2, стр.9). **Имя пакета/версия/лицензия/объём в
[UM]/[DS] не приведены** (только Reference [3] «DW3000 APIs and Simple examples release»). Для минимума
(чтение ID) драйвер **не нужен** — хватит тонкого кода поверх HAL, как для DW1000 (форматы транзакций
полностью описаны [UM] §2.3). Но для рабочего радиообмена (канал/скорость/PLL-калибровка §10, RX-tuning)
документация толкает к API [3]: *«modified software is needed since the DW3000 control register interface
is different to that of the DW1000»* ([UM] §2.2, стр.10). Решение о переносе драйвера — за владельцем
(как было с Codec2); ничего не переносили.

**Д4. Переиспользование `App/Labs/uwb_link.c` (сверено по коду).**
- *Остаётся:* каркас `Lab_Init`/`Lab_Process`, таблица команд `k_cmds[]`, `dwreset`/`spistat`, индикация
  (строки ~186–255); SPI-пламбинг `dw_cs_low/high` и правило «CSn низкий всю транзакцию» (66–97); сборка
  значения младшим октетом вперёд `val = b[3]<<24|…|b[0]` (строка 128) — DW3000 подтверждает LSB-first;
  режим SPI 0; концепция open-drain-сброса `dw_hard_reset`.
- *Меняется:* **`DW_DEVID_EXPECTED`** `0xDECA0130 → 0xDECA0302/0312` (байт MODEL 0x30→0x03) + логика
  вердикта (строка 61); **построение заголовка чтения** `dw_read_reg` — у DW1000 `hdr = reg & 0x3F`
  (bit7 read, bit6 sub, 6-битный адрес), у DW3000 иное кодирование (bit0 direction, bit1 длина, 5-битный
  base, padding-бит); **потолки SPICLK** (комментарии «INIT ≤ 3 МГц» — DW1000-специфичны; у DW3000 INIT_RC
  ≤ 7 МГц, до 38 МГц в IDLE_PLL); ветку `0xDEADDEAD` можно оставить (маркер у DW3000 сохранён, Б2), но
  сверить. **Замечание:** для регистра 0x00 заголовок `0x00` совпадает у обоих поколений, так что чтение
  именно DEV_ID сменит по сути лишь ожидаемую константу; общий формат заголовка всё равно переписать.

**Д5. Сосуществование DW1000 и DW3000 в одной работе — варианты (только предложение).** Образец из
`mks-firmware`: выбор аппаратного варианта **флагом сборки `-D`** (`board_config.h`: `-D BOARD_MKS` /
`-D BOARD_MINISTEND`, вся расходящаяся конфигурация в `#if defined(...)`, флаг прокинут в `.cproject`) +
рантайм-swap указателя для нескольких экземпляров одного чипа. **Но примера «два РАЗНЫХ драйвера
(DW1000 vs DW3000)» в mks-firmware нет** (там только DW1000 `decadriver`). Варианты для LAB09:

| Вариант | Суть | Чем платим |
|---|---|---|
| A. Флаг сборки `-D RADIO_DW3000` в одном файле | `#if`-разведение DEV_ID/заголовка/сброса внутри `uwb_link.c` | ветвление в коде и в консоли; риск «разъезда» двух веток в одном файле; но один файл работы |
| B. Отдельный файл работы (напр. `uwb_link_dw3000.c`) под тем же `LAB_ID==9` или новым | физическое разделение по `#if` на уровне файлов, как адаптеры LAB07/LAB08 над общим движком | дублирование каркаса команд; зато ветки не мешают друг другу (проверенный в проекте приём разделения) |
| C. Рантайм-детект по DEV_ID | одна прошивка читает ID и выбирает путь | самый сложный код, оба драйвера в одном образе (размер); избыточно для учебного стенда |

Рекомендация к обсуждению (выбор за владельцем): **вариант B** ближе к уже принятому в проекте стилю
«тонкий адаптер под работу» (LAB07/LAB08 над `App/Common/voice.c`) и минимизирует риск разъезда; рабочий
путь DW1000 при этом сохраняется отдельным адаптером и остаётся доступным для полноты картины (решение
Д5 владельца).

## НЕ УСТАНОВЛЕНО (нет в трёх документах)

1. **Минимальная длительность низкого импульса RSTn для DW3000** (числом) — нет ни в [UM] (§2.4–2.5,
   стр.18–23), ни в [DS] (Table 1 стр.5, Table 2 стр.11–12, §1.2 стр.3–4). Электрический параметр — в
   отдельном **DW3000 IC Datasheet** (ссылка [UM] «[5]»), которого в наборе нет. *(У DW1000 этот минимум
   = 10 нс был в даташите модуля; для DW3000 брать из IC Datasheet или задать консервативно, как делали.)*
2. **Числовое значение t10 (SPI CLK Fmax)** — ячейка Max в [DS] Table 1 (стр.5) в тексте пустая; «38 МГц»
   взято из списка фич ([UM] стр.6) и описания IDLE_PLL ([UM] Table 4, стр.19).
3. **Привязка part number `DW3110` к конкретному DEV_ID** (`0xDECA0302` vs `0xDECA0312`) — [DS] называет
   чип DW3110 (стр.1), но DEV_ID не приводит; [UM] даёт оба значения по признаку non-PDoA/PDoA, без
   сопоставления с маркировкой. *(При проверке принять оба значения как валидные — вердикт «DW3000 alive»,
   а PDoA/non-PDoA различать по младшим битам.)*
4. **Чувствительность приёмника в дБм по data rate** — нет ([DS] Table 6 только CF/BW; [UM] только
   качественно). Количественного «медленнее — дальше» внутри DW3000 в документах нет.
5. **Имя пакета драйвера DW3000, версия, лицензия, объём** — нет ([UM] §1.2 стр.9, Reference [3] стр.254).
6. **Вход собственного DC-DC платы (5 В или 3.3 В) и полная схема DWM3000EVB** — нет в [QSG]/[DS] (нужен
   schematic PDF платы). На решение это не влияет: выбрано питание с Arduino-разъёма 3V3 (положение «Up»).

Просмотренные разделы перечислены в подотчётах агентов; ключевые: [UM] §1.1–1.2, §2.2–2.10, §2.3 (SPI,
Figures 2–5), §8.2.2.1 (DEV_ID), §11, §14; [DS] §1.2 (POR), §1.3–1.3.3 (SPI), §4 (AC/Abs Max), §6.3, Table
2–9, Figure 1/8/11; [QSG] §2 Table 1, §4.1 (J1), §5 Table 4. Локально: `App/Labs/uwb_link.c`, распиновка
`PINOUT_dwm1000_lab09.md`, `mks-firmware` (`board_config.h`, `deca_port.h`, `.cproject`).

## ЧТО ЭТО МЕНЯЕТ (сводка для постановки следующего шага)

1. **Раскладка кита не меняется** — те же шесть линий SPI4/PE9–PE14; `.ioc` трогать не нужно. Единственная
   механика: RSTn на шилде выведен на D7 (CON4) — учесть в жгуте.
2. **Питание:** J1 в положение **«Up»** (3V3 с Arduino-разъёма), кит подаёт на шилд 3.3 В + GND; 5 В не
   нужно. Проверить нагрузочную способность 3 В кита (~55 мА RX).
3. **Шаг «живость/ID» переносится малой правкой `uwb_link.c`:** сменить ожидаемый DEV_ID на
   `0xDECA0302/0312`, переписать построение SPI-заголовка под формат DW3000, снять DW1000-специфичные
   пометки про «≤ 3 МГц» (у DW3000 INIT_RC ≤ 7 МГц). Каркас, консоль, сброс, спистат — переиспользуются.
4. **Тайминги сброса DW3000** брать из POR-последовательности [DS] §1.2 (INIT_RC/IDLE_RC, ~1 мс XTAL +
   ~70 µs OTP); минимум импульса RSTn в доступных документах отсутствует — либо запросить IC Datasheet,
   либо задать консервативно (как для DW1000).
5. **Инженерные образцы:** перед прошивкой прочитать наклейку модуля (`DWM3000` серийный vs `.E1.0/.E1.1`);
   у `.E1.0` — перестановка GPIO5/6.
