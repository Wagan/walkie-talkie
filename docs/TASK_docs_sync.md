# walkie-talkie

Учебный практический курс для студентов технических вузов. Цель — научиться

## Идея курса

Работа идёт этапами, от простого канала к сложному:

1. Два кита STM32F411E-DISCO соединены **проводом**; выбирается протокол передачи.
2. **Речь** прогоняется через аудио-подсистему китов туда и обратно.
3. Провод заменяется на **сменные радиомодули** — от узкополосных УКВ до UWB, чтобы
   на практике был виден выигрыш и проигрыш каждого канала связи.

Главный вывод курса, который студент получает измерением, а не на слово: сжатие речи
покупает не только влезание в канал, но и **дальность** — снижение потока позволяет
перевести радиомодуль на медленный эфирный режим, а с ним растёт чувствительность
приёмника. Простых кодеков (µ-law, ADPCM) для этого недостаточно, дальнобойные режимы
открывает только настоящий **вокодер**.

## Железо

- Два кита **STM32F411E-DISCO** со встроенными ST-LINK.
- Рабочий ноутбук (Windows), USB-хаб с внешним питанием, два кабеля USB.
- Активные колонки с джеком 3.5 мм, наушники.
- **HC-12** (433 МГц, интерфейс UART) — первый радиоканал, LAB08. Модули на руках,
  речь по эфиру проверена в поле.
- **DWM1000** (сверхширокополосный канал, интерфейс SPI) — второй радиоканал, LAB09.
  Оригинальные модули на переходных платках со штыревыми выводами, подключаются к киту
  жгутом.
- **DWM3000** (UWB следующего поколения) — для позднего этапа, в текущих заданиях не
  участвуют.
- **MAX485E** (RS-485) — отладочный стенд управления направлением полудуплекса;
  механизм разворота линии, который затем переиспользуется радиомодулями.

Прошивки разрабатываются в **STM32CubeIDE**.

## Структура папок

Проект собирается в STM32CubeIDE, а код периферии генерируется из файла
`walkie-talkie.ioc` (графический конфигуратор CubeMX внутри IDE). Важно понимать, какие
каталоги CubeMX считает **своими** и пересоздаёт при каждой генерации, а какие трогать не
будет.

**Каталоги под управлением CubeMX** — их содержимое CubeMX генерирует и может
**перезаписать или вычистить целиком** при следующей генерации кода из `.ioc`:

- `Core/` — `main.c`, обработчики прерываний, конфигурация HAL. Пользовательский код
  сюда можно писать только внутри блоков `/* USER CODE BEGIN ... */ … /* USER CODE END ... */`
  — всё, что вне этих блоков, при регенерации затирается.
- `Drivers/` — HAL и CMSIS (генерируются). Сюда же вручную положен BSP платы
  (`Drivers/BSP/`) — он переживает генерацию, но это исключение.
- `USB_DEVICE/` — стек USB Device CDC (виртуальный COM-порт консоли). Тоже
  генерируемый каталог: правки — только в блоках USER CODE.
- `Middlewares/`, `USB_HOST/` — создаются, только если в `.ioc` включён
  соответствующий компонент. **Если компонент в `.ioc` не выбран, CubeMX удаляет весь
  каталог.** Именно поэтому нельзя класть сюда ничего своего вручную.

**`ThirdParty/`** — каталог для сторонних библиотек, **вне зоны CubeMX**. Генерация кода
его не трогает. Здесь лежат:

- библиотека преобразования звука PDM→PCM:
  - `ThirdParty/PDM2PCM/Inc/pdm2pcm_glo.h` — заголовок API;
  - `ThirdParty/PDM2PCM/Lib/libPDMFilter_CM4_GCC_wc32.a` — готовая библиотека под Cortex-M4F;
- библиотека вокодера **Codec2** (лицензия **LGPL 2.1**) — используется в LAB07/LAB08.

Раньше PDM2PCM лежала в `Middlewares/…/PDM` (как в примере ST), и очередная генерация
из `.ioc` удалила её вместе со всем `Middlewares/`, из-за чего сборка падала. Перенос в
`ThirdParty/` эту проблему устраняет навсегда — по тому же правилу туда легла и Codec2.

**Документация:**

- `docs/` — задания, отчёты, методики и файлы измерений. **Входит в репозиторий
  целиком**: `TASK_*.md`, `REPORT_*.md`, результаты прогонов и всё прочее, что там
  оказывается, коммитится по умолчанию.
- `docs/reference/` — справочная документация (даташиты, reference manuals, user
  manuals в PDF). **В репозиторий не входит** (см. `.gitignore`): это большие
  сторонние файлы, они не являются исходным кодом проекта и раздували бы историю.
  Каждый работает со своей локальной копией.

## Лабораторные работы

Курс собран **одним проектом CubeIDE**: конкретная работа выбирается **конфигурацией
сборки**. У каждой конфигурации свой каталог сборки, поэтому прошивки работ не затирают
друг друга, и всегда видно, что залито в кит.

Как это устроено в коде:

- `App/Common/` — общий код, нужный всем работам:
  - трассировка `trace_swo`, `trace_log`;
  - тактирование аудио `bsp_audio_clock` (единый PLLI2S 86 МГц на вход и выход);
  - единый интерфейс работы `lab.h` (`Lab_Init` / `Lab_Process` + защита по `LAB_ID`);
  - транспорт UART `uart_port` (кольцевой DMA + IDLE, кадрирование, физслой `ttl|rs485`);
  - консоль `console`, кадрирование SLIP `frame`, аудио `audio`, кодеки `codec`;
  - раскладка приоритетов прерываний `preempt` (аудио-выход выше приёмного USART2);
  - **голосовой движок `voice`** — весь речевой тракт: кодеки, децимация с антиалиасом,
    запас по уровню входа, джиттер-буфер, Codec2, PTT, разгрузка приёмного прерывания,
    счётчики probe. Работы LAB07 и LAB08 — тонкие адаптеры поверх него.
- `App/Labs/` — по файлу на работу. Каждый файл целиком обёрнут в `#if LAB_ID == <n>`,
  так что в сборку попадает код ровно одной работы. Работа реализует две функции из
  `lab.h`: `Lab_Init()` (инициализация) и `Lab_Process()` (вызывается в основном цикле).
  `main.c` вызывает только их и при добавлении новой работы не меняется.
  - `stand_check.c` — LAB00, `uart_link.c` — LAB02, `framing.c` — LAB03,
    `voice_wire.c` — LAB04, `usb_console.c` — LAB05,
    `speech.c` — LAB07 (сжатие на проводе), `radio_voice.c` — LAB08 (речь по радио).

**Как выбрать работу.** Собрать нужную **конфигурацию сборки**: например, конфигурация
`LAB00` задаёт символ препроцессора `LAB_ID=0`. Если активна конфигурация без заданного
(или неизвестного) `LAB_ID`, сборка намеренно падает с внятным сообщением
«выберите конфигурацию работы» — это защита от заливки «не той» прошивки.

Переключение конфигурации в CubeIDE: **Project → Build Configurations → Set Active →
LAB00** (или по стрелке рядом с кнопкой молотка «Build»). Активная конфигурация видна там
же и в имени каталога сборки (`LAB00/`).

## Диагностика: консоль и SWO

У работ LAB03–LAB08 основная консоль — **USB Device CDC**: кабель в разъём USB **User**
платы (PA11/PA12), в системе появляется COM-порт, открывается любым терминалом. Команда
`help` печатает список команд активной работы. SWO используется как вспомогательный
односторонний вывод; у LAB00 и LAB02 консоли нет вовсе, там только SWO.

### SWO (SWV ITM Data Console)

**SWO** — односторонний канал трассировки (только из МК в отладчик) по одному выводу. На
STM32F411E-DISCO это вывод **PB3** (`SYS_JTDO-SWO`), заведённый на отладчик через нулевой
мост **SB15** (по умолчанию включён). Данные отправляются через **ITM** (мы шлём туда
строки и `printf`), а принимаются в STM32CubeIDE в окне **SWV ITM Data Console**. Без
подключённого отладчика вывод просто отбрасывается и кит нормально работает автономно.

**Почему не виртуальный COM-порт (VCP).** У встроенного отладчика этой платы — **ST-LINK/V2**
(на STM32F103), и **виртуального COM-порта у него нет** (VCP появляется у ST-LINK/V2-1/V3 на
платах Nucleo). Поэтому текстовая диагностика идёт по SWO, а двусторонний канал с вводом
команд реализован через USB Device CDC (впервые — в LAB05).

> Примечание: по UM1842 ST-LINK/V2 официально «supports only SWD», а вывод SWO на разъёме
> CN2 помечен как *Reserved*. Документ не гарантирует работу трассировки — но опытом на
> обеих платах курса подтверждено, что вывод доходит.

**Настройка приёма (проверенные значения):**

1. **[Run] → [Debug Configurations…]**, выбрать конфигурацию проекта, вкладка **Debugger**.
2. Интерфейс — **SWD**; включить **Serial Wire Viewer (SWV)**.
3. В [Clock Settings] задать **Core Clock = 96 МГц** (фактическая частота ядра проекта).
4. Рабочие значения, проверенные на обеих платах:
   - **Core Clock = 96 МГц**
   - **Clock Prescaler = 48**
   - **SWO Clock = 2000 кГц** (это `Core Clock / Prescaler = 96000/48 = 2000`)
   - **ITM порт 0**
5. **[Apply]**, затем **[Debug]** — запустить сессию отладки.
6. **[Window] → [Show View] → [SWV] → [SWV ITM Data Console]**.
7. Кнопкой **[Configure Trace]** включить **ITM порт 0**.
   **ВАЖНО и неочевидно:** в диалоге Configure Trace, в строке **Enable port**, порты
   пронумерованы **справа налево** — **порт 0 это самый ПРАВЫЙ** чекбокс. Легко перепутать
   и потерять минут двадцать в поисках, почему «ничего не приходит».
8. Нажать **красную кнопку [Start/Stop Trace]** в окне консоли (без неё приём не идёт).
9. **Resume** — строки диагностики (`[I] …`, `[E] …`) пойдут во вкладку **Port 0**.

**Тактовую частоту 96 МГц не поднимать.** При 100 МГц VCO даёт 400 МГц, и целого делителя
для 48 МГц USB не остаётся — пропадает USB-консоль, основной инструмент отладки курса.

Второй радиоканал курса — сверхширокополосный, на модулях **DWM1000** (оригинальные, на

ложится на существующий транспорт и голосовой движок, что за модуль, распиновка,
отличия от HC-12.

Модули **DWM3000** (UWB следующего поколения) — материал более позднего этапа.
