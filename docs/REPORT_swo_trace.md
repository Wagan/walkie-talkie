### Поведение вывода без отладчика / при выключенной трассировке (критично)
Используется штатная `ITM_SendChar()` из `core_cm4.h`. По её фактическому исходнику:
```c
if ((ITM->TCR & ITM_TCR_ITMENA_Msk) && (ITM->TER & 1)) {   // ITM включён И порт 0 включён
    while (ITM->PORT[0].u32 == 0) { __NOP(); }              // ждать готовности FIFO
    ITM->PORT[0].u8 = (uint8_t)ch;
}
return ch;
```
Биты `TCR.ITMENA` и `TER[0]` выставляет **отладчик** при включении SWV. Поэтому:
- **Без отладчика (или при выключенной трассировке) условие ложно** → функция не входит в
  цикл ожидания, не пишет в FIFO и **сразу возвращает управление, отбросив символ**. Ядро
  **не блокируется** — прошивка нормально работает автономно (важно для питания без отладчика).
- Busy-wait `while(PORT[0].u32==0)` достижим **только** когда отладчик уже включил ITM и порт 0
  (активная трассировка); тогда возможна кратковременная задержка, если приёмник SWO не
  успевает вычитывать. На автономный кит это не влияет.

Итог по пункту A2: **сразу возвращает управление и отбрасывает символ; не блокируется** (кроме
случая активной трассировки с непрочитанным FIFO).

## C. Последовательность настройки SWV в STM32CubeIDE 1.16.0

По UM2609 Rev 18 (§3.2.2.1 «SWV debug configuration» и §3.2.3.5 «SWV ITM Data Console»).

**Наш Core Clock = 96 МГц** — фактическая частота ядра из нашей конфигурации тактирования
(`.ioc`: `RCC.SYSCLKFreq_VALUE = RCC.HCLKFreq_Value = RCC.CortexFreq_Value = 96000000`;
переменная `SystemCoreClock` после `SystemClock_Config()` = 96000000). Именно 96 МГц вписывать
в поле [Core Clock].

Шаги (Debug Configurations → наша конфигурация STM32 Cortex-M):
1. **[Run] > [Debug Configurations…]**, выбрать конфигурацию проекта; вкладка **Debugger**.
2. Интерфейс: выбрать **[SWD]** (SWV работает только по SWD — §3.2.2.1).
3. Включить **[SWV]** (Serial Wire Viewer).
4. В [Clock Settings] задать **[Core Clock] = 96 (МГц)** — «must correspond to the value set by
   the application». Проверить можно, добавив `SystemCoreClock` в Expressions в отладке.
5. **[SWO clock]**: по умолчанию **вручную задавать не нужно** — IDE ставит максимально возможную
   частоту в зависимости от зонда и Core Clock. Если аппаратура не тянет высокую частоту SWO,
   включить **[Limit SWO clock]** и вписать предел в кГц. (Про поведение при неверном Core Clock
   UM2609 явной фразы не даёт — по построению неверный Core Clock приводит к неверному расчёту
   делителя SWO и, как следствие, к отсутствию/искажению данных; это логическое следствие, не
   дословная цитата документа.)
6. **[Apply]**, затем **[Debug]** — запустить сессию (зонд и плата подключены).
7. **[Window] > [Show View] > [SWV] > [SWV ITM Data Console]** — открыть консоль.
   (Для первого раза полезен и **[SWV Trace Log]** — видно, идут ли пакеты вообще.)
8. В открытой консоли/настройках трассировки включить **[ITM port 0]** (наш `TRACE_SWO_ITM_PORT`).
   Кнопка **[Configure Trace]** есть во всех SWV-видах; там же ITM Stimulus Ports (32 порта).
9. Нажать **красную кнопку [Start/Stop Trace]** на панели консоли — запустить приём.
10. Пустить программу (Resume) — строки `SWO <n>` пойдут во вкладку **Port 0**.

Чем запускается приём: именно кнопкой **[Start/Stop Trace]** (красная) в SWV-виде; без её нажатия
данные не отображаются, даже если сессия идёт.

Чего подтвердить нечем: UM2609 описывает процедуру обобщённо для STM32CubeIDE (Rev 18 документа),
не привязываясь к 1.16.0; расположение пунктов меню в 1.16.0 совпадает. **Отдельно:** документ
UM1842 не подтверждает работоспособность SWO именно на этой плате (вывод CN2 «Reserved», ST-LINK/V2
«supports only SWD») — поэтому факт прохождения трассы проверяется только опытом (это и есть цель
Части 1).

## D. Запасной вариант (без реализации): наблюдение без остановки ядра

Если SWO не заработает — основной запасной путь до появления USB CDC — **Live Expressions**
(STM32CubeIDE, UM2609 §3.1.6.1):
- Работает **поверх обычного SWD** — SWO/SWV не требуется. UM2609: «All three GDB servers support
  normal debug, live expressions and SWV». То есть на нашем ST-LINK/V2 (только SWD) сработает
  независимо от того, идёт ли трасса по SWO.
- **Не останавливает ядро:** значения выражений «sampled live during debug execution» — обновляются
  периодически, пока программа выполняется (без halt).
- Включается флажком **[Enable live expressions]** в Debug Configurations (по умолчанию включён).
  Вид: **[Window] > [Show View] > [Live Expressions]**; добавить туда глобальные переменные
  (напр. счётчик блоков, флаг ошибки из демо) и/или выражения вида `(i*4+offset)`.
- **Ограничения (UM2609):** (1) чем больше выражений — тем ниже частота опроса
  («An increased number of expressions being sampled results in a slower sample rate»);
  (2) показывает только **значения переменных/выражений**, а не поток текста/лог; (3) переменные
  должны быть **глобальными** (в памяти) и в области видимости; (4) нужна **активная сессия отладки**
  (зонд подключён) — это не автономная диагностика; (5) это опрос памяти по SWD, не событийный
  real-time поток.

Прочее (кратко, тоже без реализации): при отсутствии SWO и Live Expressions остаётся классический
приём — остановки на брейкпойнтах и просмотр переменных (но это уже с остановкой ядра), либо
позднее — двунаправленный канал по **USB Device CDC** (следующая лаба). Индикация светодиодами демо
(LED4/5/6) продолжает работать без отладчика как грубая диагностика.
