## Задача A. Инструкция для владельца по CubeMX (`.ioc`)

Открыть `walkie-talkie.ioc` в CubeMX. По шагам:

### A.1. Включить USB_OTG_FS как устройство и отключить контроль VBUS (освободить PA9)

1. **Connectivity → USB_OTG_FS → Mode = `Device_Only`.**
   Это задействует ТОЛЬКО PA11 (USB_OTG_FS_DM) и PA12 (USB_OTG_FS_DP) — обязательные линии
   USB FS. В `.ioc` сейчас PA11/PA12 не заняты (проверено: в файле есть только PA9=USART1_TX
   и PA10=USART1_RX, записей PA11/PA12 нет), конфликта нет.
2. Вкладка **USB_OTG_FS → Parameter Settings → «Activate VBUS Sensing» → `Disabled`**
   (подпись пункта — по UI CubeMX; генерируемый параметр подтверждён кодом:
   `hpcd.Init.vbus_sensing_enable = 0`, `usbd_conf.c:324`). Именно отключение VBUS sensing
   убирает захват **PA9** под сигнал VBUS — PA9 остаётся за USART1_TX. Если VBUS sensing
   оставить включённым, CubeMX попытается назначить PA9 = USB_OTG_FS_VBUS и покажет конфликт
   с USART1_TX.
3. Там же держать **SOF output = Disabled** (эталон: `hpcd.Init.Sof_enable = 0`,
   `usbd_conf.c:322`) — SOF не нужен и лишних пинов не потребует.

### A.2. Убедиться, что PA10 остаётся за USART1_RX (не уходит под ID)

- Сигнал **ID** (и Host/Dual-role) в режиме **`Device_Only`** НЕ используется, поэтому PA10
  под ID не забирается. Дополнительно: PA9 и PA10 в `.ioc` помечены `Locked=true`
  (`PA9.Locked=true`, `PA10.Locked=true`), что защищает их назначение при пересчёте пинов.
- Контроль: после включения USB в **Pinout view** PA10 должен остаться подсвечен как
  `USART1_RX`, PA9 — как `USART1_TX`. Если какой-то из них перекрасился в USB — вернуться к
  шагу A.1.2 (VBUS sensing) и проверить, что режим именно `Device_Only`, а не `Host`/`Dual`.

### A.3. Выбрать класс USB Device (CDC) и его параметры

1. **Middleware → USB_DEVICE → активировать; «Class For FS IP» = `Communication Device
   Class (Virtual Port Com)`** (подпись — по UI CubeMX; это и есть класс CDC, библиотека
   которого лежит в `Middlewares/.../Class/CDC`).
2. Значимые параметры класса:
   - VID/PID и строки — оставить дефолт ST (VID `0x0483`, PID `0x5740`). На этот PID Windows
     10/11 сам ставит встроенный драйвер `usbser.sys` (Virtual COM), отдельный драйвер не
     нужен (детали — Задача D, пишется позже).
   - Скорость — **Full Speed** (единственная для встроенного PHY F411: `PCD_SPEED_FULL`,
     `phy_itface = PCD_PHY_EMBEDDED`, `usbd_conf.c:321-323`).
   - Буфера приёма/передачи CDC (`APP_RX_DATA_SIZE`/`APP_TX_DATA_SIZE`) правятся уже в коде
     `usbd_cdc_if.c` (USER CODE) на этапе Задачи B, не в конфигураторе.

### A.4. Прерывания

- **NVIC Settings → включить `USB OTG FS global interrupt`** (генерирует вектор
  `OTG_FS_IRQHandler` и `HAL_NVIC_EnableIRQ(OTG_FS_IRQn)` — эталон `usbd_conf.c:73-76`).
- Приоритет: не критичен, оставить численно НИЖЕ (больше по числу), чем у UART/DMA. У нас
  USART1 и DMA2_Stream2 стоят на приоритете 0; USB можно оставить на дефолте CubeMX (в
  эталоне — 6), чтобы USB не вытеснял приём по DMA. Группировка приоритетов в проекте —
  `NVIC_PRIORITYGROUP_0`.

### A.5. Тактирование USB (48 МГц) — проверено, менять НЕ нужно

Фактически по `.ioc` (сверено с `Core/Src/main.c`):
- HSE = 8 МГц (кварц), `PLLM=4` → вход VCO 2 МГц; `PLLN=192` → VCO 384 МГц;
- `PLLP=DIV4` → SYSCLK 96 МГц; **`PLLQ=8` → PLL48CK = 384/8 = 48.000 МГц.**
- В `.ioc` это уже зафиксировано: `RCC.48MHZClocksFreq_Value=48000000`,
  `RCC.PLLQCLKFreq_Value=48000000`.

Вывод: **частота USB (48 МГц) обеспечивается штатно текущим PLLQ, ничего в тактировании
менять не требуется.** После включения USB в Clock Configuration поле «USB clock (MHz)»
должно показывать 48 и не быть красным. Если CubeMX почему-то покажет иное — не подгонять
вручную, а STOP и вопрос владельцу (расхождение с фактом).

### A.6. На что это повлияет из уже работающего

- **USART1 (LAB02):** не затрагивается при условии, что VBUS sensing отключён (A.1.2) — иначе
  конфликт за PA9. Это единственный реальный риск, проверить в Pinout (A.2).
- **LAB00 (аудио):** использует I2S2/I2S3 на отдельном `PLLI2S` (`PLLI2SM=5, PLLI2SN=200`),
  не связан с `PLLQ`. USB на аудио не влияет.
- **Регенерация:** CubeMX ЗАКОННО положит библиотеку USB Device в `Middlewares/` и создаст
  генерируемые файлы `USB_DEVICE/App/usb_device.c`, `usbd_desc.c`, `usbd_cdc_if.c`,
  `usbd_conf.c` + вызов `MX_USB_DEVICE_Init()` в `main.c`. Наш код (`App/Labs/uart_link.c`,
  `App/Common/*`) при этом не трогается. **Важно (урок Middlewares):** свой код консоли туда
  НЕ класть — он пойдёт в `App/Common` и `App/Labs`; в генерируемых файлах (напр.
  `usbd_cdc_if.c`) — только внутри блоков USER CODE.
- `PLLQ` сейчас, кроме USB, номинально относится и к SDIO/RNG — они в проекте не используются,
  влияния нет.

### A.7. Что вернуть исполнителю после регенерации

Чтобы продолжить с Задачами B–E, подтвердить, что появились: каталог `USB_DEVICE/`,
файлы `usbd_cdc_if.c`/`usbd_conf.c`/`usbd_desc.c`, вектор `OTG_FS_IRQHandler` в
`Core/Src/stm32f4xx_it.c`, вызов `MX_USB_DEVICE_Init()` в `main.c`, и что PA9=USART1_TX /
PA10=USART1_RX сохранились. После этого — сигнал исполнителю продолжать.

## Задача B. Модуль консоли (`App/Common/console.{h,c}`)

Консоль сделана общим модулем (нужна не одной работе). Компилируется только там, где нужна —
файл `console.c` обёрнут в `#if LAB_ID == 5`, поэтому LAB00/LAB02 не затрагивает.

- **Приём строк.** Из колбэка USB `CDC_Receive_FS` вызывается `Console_RxFromISR()` — она
  ТОЛЬКО складывает принятые байты в кольцевой буфер (256 Б), без разбора (короткий ISR при
  общем приоритете 0). В основном цикле `Console_Process()` собирает строки: символом-
  разделителем считается любой из CR/LF (разные терминалы шлют по-разному), пустые строки
  (второй символ CRLF) игнорируются, Backspace/DEL стирают последний символ. Готовая строка
  разбирается на `argv[]` по пробелам/табам (как argc/argv в main).
- **Таблица команд.** `Console_Register(таблица, число)` принимает массив
  `{имя, описание, обработчик}`. Добавление команды не требует правок разбора. Диспетчер ищет
  имя в таблице; встроенная команда `help` печатает список зарегистрированных команд с
  описаниями.
- **Вывод и интеграция с TRACE.** `Console_Printf`/`Console_Write` кладут текст в передающее
  кольцо (2048 Б), которое `Console_Process()` выталкивает в USB порциями по 64 Б неблокирующе
  (через `CDC_Transmit_FS`, с учётом `USBD_BUSY` — данные при занятости не теряются). Чтобы
  существующие `TRACE_LOG`/`TRACE_ERR` шли И в SWO, И в USB, в `trace_swo.c` добавлен слабый
  хук `Trace_UsbPutChar()` (по умолчанию пустой — у LAB00/LAB02 поведение SWO не меняется);
  `console.c` даёт ему СИЛЬНОЕ определение, дублируя вывод printf в USB. Так ничего в
  имеющемся коде трассировки не сломано, а мультиплексирование включается самим фактом
  линковки консоли (только LAB05).
- Из ISR ничего не печатается и не разбирается — только буферизация.

## Задача C. Работа LAB05 (`App/Labs/usb_console.c`, `LAB_ID=5`) и разделение приёма

**Разделение кода приёма (не сломав LAB02).** Весь транспорт по USART1 вынесен в новый общий
модуль `App/Common/uart_port.{h,c}` (обёрнут `#if (LAB_ID == 2) || (LAB_ID == 5)`): кольцевой
DMA-приём с IDLE, сборка пакетов, ресинхронизация по CRC, статистика, CRC, передача пакета/
байта, смена скорости, сырой dump-буфер, все HAL-колбэки USART1. Лаборатория-потребитель
добавляет только своё через слабые хуки `UartPort_OnRxOk/OnError/OnTxDone` (по умолчанию
пустые). LAB02 (`App/Labs/uart_link.c`) переписан в тонкий адаптер над `uart_port`: те же
светодиоды, те же режимы PERIODIC/LOAD, **тот же формат строк статистики** — наблюдаемое
поведение LAB02 сохранено 1:1. LAB05 использует тот же `uart_port`, но со своими командами.

**Команды LAB05:** `help` (встроенная), `send [n]`, `sendbyte <val>` (dec/0x), `stat`,
`reset`, `dump` (hex последних сырых принятых байт — все байты пишутся в dump-буфер до
разбора на пакеты, независимо от того, собрался пакет или нет), `baud <speed>` (реинициализация
USART1 на лету: `HAL_UART_DeInit`→смена BaudRate→`HAL_UART_Init`→перезапуск приёма).

**Команда `loop` НЕ реализована — обоснование по RM0383.** У USART STM32F411 **нет**
аппаратного режима самопроверки/внутреннего loopback: в регистрах CR1/CR2/CR3 такого бита нет
(поиск по RM0383 «loopback/self-test/test mode» даёт совпадения только для USB OTG и I2C, не
для USART). Ближайшее — HDSEL (single-wire half-duplex): он внутренне связывает приём с линией
TX, но это НЕ документированный self-test, требует PA9 как единственный провод с открытым
стоком и подвержен контеншену с внешней линией. Поэтому «петли без внешних проводов» здесь нет;
команда не сделана (по правилу задачи), для проверки без второй платы — внешняя перемычка
PA9↔PA10. Об этом сказано и в `docs/LABS.md`.

## Задача D. Что делать, если USB не заработает

- **Проверить определение в Windows.** Диспетчер устройств → «Порты (COM и LPT)»: должно
  появиться `USB Serial Device (COMxx)`. Драйвер встроенный (`usbser.sys`, Win10/11) —
  отдельный `.inf` не нужен. Если устройство висит в «Другие устройства» с восклицательным
  знаком или как «Unknown Device» — см. ниже.
- **Индикация на плате.** Зелёный LED4 мигает ~2 Гц, когда хост СКОНФИГУРИРОВАЛ устройство и
  порт можно открывать (`Console_IsConfigured()` → `dev_state == USBD_STATE_CONFIGURED`).
  Не мигает → перечисление не завершилось.
- **Что смотреть в первую очередь, если порт не появляется:**
  1. Кабель — именно в разъём USB **User** (не ST-LINK) и кабель data-, не charge-only.
  2. Тактирование USB: 48 МГц (PLLQ=8). Если PLL/HSE не поднялись — USB не перечислится;
     проверить, что прошивка вообще стартовала (SWO-баннер LAB05).
  3. VBUS sensing должен быть выключен (иначе без реального VBUS на PA9 стек может не
     стартовать). В нашей конфигурации отключён (см. Задача A).
  4. Дескрипторы/питание: при первом включении Windows может кэшировать «плохое» перечисление
     — переткнуть кабель, сменить порт USB.
  5. SWO-диагностика продолжает работать параллельно (USB её не заменяет) — по ней видно, что
     ядро живо и `Lab_Init` прошёл.

## Что проверить владельцу и как выглядит успех

1. Выбрать конфигурацию сборки **LAB05** (Project → Build Configurations → Set Active → LAB05),
   собрать, прошить один кит.
2. Открыть появившийся COM-порт терминалом. Ожидается баннер `LAB05 USB console ready. Type
   'help'.` и мигающий зелёный LED4.
3. Набрать `help` — список команд. `stat` — статистика. `sendbyte 0x55` при замкнутых PA9↔PA10
   (или подключённой второй плате) — затем `dump` должен показать пришедший `55`. `send 5` —
   отправить пакеты, снова `dump`/`stat`. `baud 9600` — сменить скорость.
4. **Успех:** команды исполняются, вывод виден в терминале; `dump` показывает реально принятые
   байты; на замкнутой линии отправленное возвращается. Это и есть инструмент для дальнейшей
   отладки провода.
