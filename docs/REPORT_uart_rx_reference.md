# Отчёт: TASK_uart_rx_reference

Read-only разведка (правила задачи: только чтение, ничего не менять/не коммитить). Все
выводы — со ссылками на файлы/строки в `STM32Cube_FW_F4_V1.28.0` и в нашем
`App/Labs/uart_link.c`.

## Краткий вывод

**Гипотезу про «лавину ошибок кадра внутри приёмника» факты HAL опровергают.** Ошибка
кадра (FE) в режиме приёма по прерыванию у F4 — **неблокирующая**: приём не прерывается,
уже принятые байты не теряются, `RxState` остаётся `BUSY_RX`, а сбойный байт всё равно
кладётся в буфер и считается. Перезапускать приём после FE не требуется — HAL продолжает
сам. Наш код по обработке ошибок не хуже, а строже эталонного IT-примера ST.

Симптом «rx=0 при том, что FE только ~3 из 10 пакетов» указывает не на побайтовую, а на
**пакетную рассинхронизацию**: приёмник читает непрерывный поток с неверного байтового
смещения, поэтому CRC не сходится у **всех** пакетов, а не только у тех, где был FE. Это
ровно та проблема, которую в архитектуре фиксированной длины закрывает кадрирование
(LAB03) и, надёжнее всего, **приём по DMA с прерыванием по простою линии (IDLE)** —
эталон для этого в пакете есть.

## Задача A. Эталонные примеры из пакета

Проекты под наш кит есть: `Projects/STM32F411E-Discovery/Examples/UART/` —
`UART_TwoBoards_ComPolling`, `ComIT`, `ComDMA`. Плюс современный образец непрерывного
приёма — `Projects/STM32446E-Nucleo/Examples/UART/UART_ReceptionToIdle_CircularDMA` (и
такой же на F429ZI-Nucleo).

**1. UART_TwoBoards_ComIT** (приём по прерыванию — прямой аналог нашего):
- Размер приёма — **фиксированный блок целиком** (`aRxBuffer`, `RXBUFFERSIZE`), один
  запуск `HAL_UART_Receive_IT(...RXBUFFERSIZE)` — `main.c:143,153`.
- В `HAL_UART_RxCpltCallback` (`main.c:280-287`) приём **НЕ перезапускается**: ставится
  флаг `UartReady=SET` и зажигается LED. Обмен одноразовый, не поточный.
- `HAL_UART_ErrorCallback` (`main.c:296-300`): **только зажигает LED3**, ничего не
  перезапускает и флаги явно не сбрасывает. Эталонный IT-пример **не рассчитан на
  восстановление** после ошибки.
- **Вывод:** наш `uart_link.c` по надёжности приёма **строже** этого эталона (мы
  перезапускаем приём и в RxCplt, и в ErrorCallback). Копировать «как в референсе» нечего.

**2. UART_TwoBoards_ComDMA** (приём по DMA):
- USART здесь — **USART2** (`Inc/main.h:32`), DMA — **DMA1 Stream5 RX / Stream6 TX,
  канал 4** (`main.h:50-53`). Это маппинг USART2, не USART1.
- Режим DMA — **`DMA_NORMAL`**, не circular (`stm32f4xx_hal_msp.c:114`). Приём на один
  фиксированный блок, сценарий одноразовый. Границы данных не решаются — длина известна.

**3. UART_ReceptionToIdle_CircularDMA** (непрерывный приём неизвестной длины — ближе
всего к LAB04):
- Приём запускается один раз: `HAL_UARTEx_ReceiveToIdle_DMA(&huart2, aRXBufferUser,
  RX_BUFFER_SIZE)` (`main.c:295`), DMA — **circular**.
- Границы данных решаются через `HAL_UARTEx_RxEventCallback(huart, Size)` (`main.c:345`),
  который вызывается на трёх событиях: **DMA Half-Transfer, DMA Transfer-Complete и UART
  IDLE**. `Size` — сколько байт в кольце уже лежит; приложение хранит `old_pos` и забирает
  новый кусок `[old_pos, Size)` (`main.c:352-396`).
- **Штатный ответ ST на «непрерывный поток без пауз».** Приём никогда не останавливается,
  между «пакетами» нет окна потерь → нет рассинхронизации из-за перезапуска.

## Задача B. Что делает сам HAL при ошибке (ключевой пункт)

По `Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_uart.c`.

**B1. FE во время активного `Receive_IT` — приём НЕ прекращается.**
В `HAL_UART_IRQHandler` (`:2350`):
- `errorflags = SR & (PE|FE|ORE|NE)` (`:2359`). При FE — ветка ошибок.
- `ErrorCode |= FE` (`:2387-2390`).
- При FE байт уже в `DR` и `RXNE=1`, поэтому вызывается `UART_Receive_IT(huart)`
  (`:2403-2406`) — он **читает `DR`, кладёт (испорченный) байт в буфер, делает
  `--RxXferCount`** (`:3616,3622,3625`). Байт **поглощается и считается как обычный**.
- Далее `dmarequest=0` (DMA нет), ORE не выставлен → условие блокирующей ошибки
  `(ORE || dmarequest)` **ложно** (`:2411`) → **неблокирующая** ветка (`:2459-2472`):
  вызывается `HAL_UART_ErrorCallback`, затем `ErrorCode=NONE`. **`RxState` остаётся
  `BUSY_RX`, дескриптор приёма жив, принятые байты целы.**

**Итог B1:** после FE/NE/PE перезапускать приём не нужно — он продолжается сам с той же
позиции, байтовое выравнивание HAL сохраняет (каждый байт считается ровно один раз).
Одна FE = один мусорный байт = одна ошибка CRC. Самоподдерживающейся «лавины» на уровне
HAL от FE не возникает.

**B2. ORE (переполнение) — единственная блокирующая ошибка.**
Только при ORE (или любой ошибке в DMA-режиме) HAL зовёт `UART_EndRxTransfer` (`:2416`),
который **отключает RXNE/PE/ERR-прерывания и ставит `RxState=READY`** (`:3335-3350`).
Здесь приём реально останавливается и его **надо перезапускать вручную** — что наш код и
делает. Не перезапустишь — приёма больше не будет.

**B3. Сброс флагов ошибок (F4).**
PE/FE/NE/ORE сбрасываются последовательностью **чтение `SR`, затем чтение `DR`**. В
обработчике `SR` читается сверху (`:2352`), `DR` — внутри `UART_Receive_IT`. Пока `RXNE`
выставлен (при FE — выставлен), последовательность выполняется и флаги гаснут. ORE при
старте нового приёма чистится явно `__HAL_UART_CLEAR_OREFLAG` (`:1511`). Бесконечного
повторного срабатывания одной ошибки HAL сам по себе не порождает.

**Вердикт по гипотезе:** факты HAL её **опровергают**. Механизма «после первой FE
приёмник теряет выравнивание и генерирует лавину FE» в IT-режиме F4 нет — FE
неблокирующая и выравнивание не рушит.

## Задача C. Сравнение с нашим кодом

| Аспект | Эталон (ComIT / ReceptionToIdle) | Наш `uart_link.c` | Отличие → симптом? |
|---|---|---|---|
| Размер приёма | Фикс. блок / кольцо целиком | Фикс. блок `LAB02_PACKET_SIZE` (`:176,319`) | Как в ComIT. Кольца/IDLE нет → **да**, нет ресинхронизации по паузе |
| Перезапуск в RxCplt | ComIT — **не** перезапускает | Перезапускаем сразу (`:319`) | Мы надёжнее для потока |
| Обработка ошибок | ComIT — только LED (`:296`) | Считаем ORE/FE/PE/NE + rearm (`:331-338`) | Мы строже. Rearm после FE — **безвредный no-op**: `RxState` ещё `BUSY_RX`, `HAL_UART_Receive_IT` вернёт `HAL_BUSY` (`:1347-1350`); реально срабатывает только после ORE — и это правильно |
| Границы пакета/ресинхр. | ReceptionToIdle — по IDLE+`old_pos` | **Нет** (это LAB03) | **Ключевое.** Сдвиг на 1 байт двигает границу пакета навсегда |

**Про «окно неактивности приёма».** Для FE окна **нет** — приём не останавливается. Окно
есть только для ORE: от `UART_EndRxTransfer` до нашего `HAL_UART_Receive_IT` в
`ErrorCallback` — единицы микросекунд (десятки инструкций на 96 МГц). На 115200 байт идёт
~87 мкс, за это окно теряется 0 байт. Но **любая** потеря/вставка одного байта (например
от единичного ORE) сдвигает 30-байтовую границу пакета **навсегда**, и дальше CRC не
сходится у всех пакетов.

**Почему это согласуется с наблюдением, а гипотеза-лавина — нет.** Держись выравнивание,
при FE у ~30% пакетов остальные ~70% проходили бы CRC и `rx` был бы ≈70% от `tx`.
Наблюдаемое `rx=0` при FE 3/10 означает, что CRC не сходится **ни у одного** пакета — то
есть приёмник читает поток со **сдвинутого байтового смещения**. Поле CRC попадает на
чужие байты (universal CRC-fail), стоп-биты периодически семплируются как данные → отсюда
спорадические FE. Это картина **пакетной рассинхронизации**, а не «FE-лавины».

## Задача D. Известные готовые решения непрерывного приёма на STM32

**1. DMA в кольцевой буфер + прерывание по IDLE** (`HAL_UARTEx_ReceiveToIdle_DMA`,
эталон `UART_ReceptionToIdle_CircularDMA`).
- DMA circular непрерывно пишет в кольцо; приложение по HT/TC/IDLE узнаёт позицию записи
  (`Size`) и забирает новый кусок. Приём **никогда не останавливается**.
- Устойчив: нет окна перезапуска → нет потерь на стыке → байтовый сдвиг не копится; пауза
  (IDLE) отмечает границу сообщения — точка **ресинхронизации**. Одиночная FE портит один
  байт, но не двигает границу.
- Нужно в конфигураторе: **DMA-поток для USART1_RX** + прерывание USART1 (для IDLE) +
  прерывание DMA-потока.
- Для LAB04 (звук) — **целевая архитектура**; аудио-тракт уже работает по той же модели
  callback'ов.

**2. DMA circular без IDLE, опрос `NDTR`/`__HAL_DMA_GET_COUNTER`** — то же кольцо, но
позицию читаем сами по таймеру/в цикле. Проще (без IDLE-IRQ), задержка = период опроса.
Устойчивость к сдвигу та же.

**3. Приём по прерыванию по 1 байту + свой автомат кадра** — `Receive_IT(...,1)`, в
RxCplt складываем байт в кольцо/парсер, ищем префикс кадра. Устойчив за счёт
ресинхронизации по маркеру (фактически LAB03). Для непрерывного аудио хуже DMA.

Общее: устойчивость даёт не сам DMA, а **отсутствие окна перезапуска + точка
ресинхронизации** (IDLE-пауза или маркер кадра). Фиксированная длина без того и другого
(наш LAB02) обречена «залипнуть» после первого сдвига.

## Задача E. Рекомендация

По фактам A–D наиболее вероятная причина — **не настройка UART и не обработка ошибок**
(тут наш код корректен и строже эталона), а **пакетная рассинхронизация**: приёмник
фиксированной длины без кадрирования и без ресинхронизации по паузе, единожды сдвинувшись
на байт, читает поток с неверного смещения → CRC не сходится у всех пакетов (`rx=0`), а
стоп-биты периодически дают FE. Гипотезу «FE-лавина внутри HAL» факты драйвера
опровергают.

**Самый короткий и надёжный путь** — перевести приём на **`HAL_UARTEx_ReceiveToIdle_DMA`
в кольцевой буфер (DMA circular) с разбором по `RxEventCallback`** (эталон
`UART_ReceptionToIdle_CircularDMA`): убирает окно перезапуска, IDLE даёт ресинхронизацию
по границе сообщения; попутно это целевая архитектура для LAB04. Быстрый промежуточный
тест без переделки железа: временно перейти на побайтовый `Receive_IT(...,1)` со сборкой
пакета — если `rx` станет ненулевым, диагноз «сдвиг кадра» подтверждён.

Это требует **включить DMA для USART1 в `.ioc`** (сейчас его нет: `USART1.VirtualMode=
VM_ASYNC`, DMA-запросов USART1 в файле нет — `walkie-talkie.ioc:326-327`), а править
`.ioc` — прерогатива владельца. Конкретно для **USART1 на STM32F411 (RM0383, DMA2 request
mapping)** — потоки **DMA2** (USART1 висит на DMA2, не DMA1):

- **USART1_RX → DMA2, Stream 2, Channel 4** (альтернатива — Stream 5, Channel 4);
- **USART1_TX → DMA2, Stream 7, Channel 4**.

Для приёма по IDLE достаточно завести **RX-поток** (Stream2 или Stream5, ch4) в circular,
включить прерывание USART1 (NVIC USART1 global interrupt) и прерывание выбранного
DMA2-потока. TX по DMA (Stream7 ch4) — опционально, пригодится для LAB04.
