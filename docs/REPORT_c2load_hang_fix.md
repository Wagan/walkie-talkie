# Отчёт: c2load вешал плату (регресс шага `5e7ffbc`) — причина и правка

`c2load` на `5e7ffbc` вешал плату (главный цикл вставал, консоль мертва). Разобрано по коду, не
гаданием. Правок исходников Codec2 нет; тракт/лесенка/кадрирование/probe A/B/C не трогались.
Сборка LAB00/02/03/04/05/07 — **0 ошибок, 0 предупреждений**.

## Причина — замер стека (кандидат 2), не пул

**Виноват новый несатурируемый замер стека.** В `5e7ffbc` `stk_paint()` заливала **всю свободную
область стека** `[end+0x600 … SP−512)` (≈86 КБ) значением `0xA5A5A5A5`, и это делалось **15 раз**
(3 операции × 5 режимов), guard всего **512 Б** (`speech.c` в `5e7ffbc`: `stk_paint`, `STK_GUARD 512`).

Ключ: после шага NVIC аудио-выход — **высшего приоритета и прерывает всё** (`Preempt_AudioOutHighest`).
Его кадр прерывания (аппаратный стек-фрейм + ленивое сохранение FPU = 104 Б, плюс цепочка
`Audio_FillPlayback`→`BSP_AUDIO_OUT_ChangeBuffer`→`HAL_I2S_Transmit_DMA`) глубже 512 Б. Пока
`stk_paint` пишет `0xA5` в зону `[…, SP−512)`, срабатывает аудио-ISR и кладёт свой кадр в
`[SP−nesting, SP)` — часть кадра ниже `SP−512` попадает в заливаемую область. Заливка затирает
**живой адрес возврата / регистры ISR** → возврат из прерывания по `0xA5A5A5A5` → HardFault →
главный цикл стоит, LED гаснет, консоль мертва. Это ровно наблюдавшиеся симптомы.

Почему старая `961e9a2` не вешала: там заливка была **один раз** и меньшим окном; новая версия
залила огромную зону **15 раз** при активном высокоприоритетном аудио-ISR — экспозиция гонки выросла
на порядки, отказ стал стабильным.

**Кандидат 1 (пул) исключён фактом:** прошлый прогон печатал `stateRAM = 9376 B` для ВСЕХ режимов,
это максимум расхода create (high-water пула). `9376 < 16384` → `codec2_malloc` не возвращал NULL,
разыменования нуля не было. Пул не при чём.

## Правка (`App/Labs/speech.c`)

1. **Замер стека переделан безопасно** (`stk_paint`/`stk_used`): заливка/скан идут **под запретом
   прерываний** (`__disable_irq`/восстановление `PRIMASK`) — во время самой заливки НИ ОДИН ISR не
   трогает стек, гонка невозможна. Окно ограничено `STK_WINDOW = 56 КБ` (несатурируемо для ~40 КБ,
   и заведомо выше bss/пула — не задевает не-стековые данные), верх окна на `STK_GUARD = 256 Б`
   ниже SP. Прерывания во время самой операции (encode/decode, НЕ заливки) законно используют
   залитую зону — это и есть измеряемая высокая вода. Насыщение (если вдруг > окна) помечается
   `(SAT!)`.
2. **Пул не молчит при нехватке** (кандидат 1, по просьбе — превентивно): `codec2_malloc` ставит
   флаг `c2PoolFail` при возврате NULL; `c2load` после `create` проверяет его и NULL, печатает
   «ПУЛ ИСЧЕРПАН (нужно > N B) — режим пропущен» и корректно продолжает (не падает).

## Доработки команды (договорённость для долгих команд)

- **Одиночный режим:** `c2load 3200` (или 2400/1600/1300/700C) — гоняет один режим для локализации;
  без аргумента — все.
- **Прогресс:** перед `create` и перед каждым входом (`silence/tone/noise`) печатается строка и
  **выталкивается `Console_Flush()`** (неблокирующе, ограничено), поэтому видно, что плата жива и на
  каком шаге. Итоговые строки тоже флашатся.
- **Тайминги:** длительность каждого режима (столбец `ms`) и общая (`total N ms`) — по разностям
  `HAL_GetTick()`.
- **Итераций меньше:** 30 → **8** на вход (максимум по 8×3 входам стабилен; на достоверность
  худшего случая не влияет — он определяется видом входа, а их три).
