## 2. Пункт 1 — сброс модуля первым шагом `uwbinit`

**Найденная причина отказа (факт из кода, не предположение).** `radio_init()` (`dw3000_port.c`)
после `Dw3000Port_Probe()` ждёт `dwt_checkidlerc()` с таймаутом 10 мс (было `dw3000_port.c`,
цикл ожидания IDLE_RC). По документации драйвера (`ThirdParty/dw3000_driver/dwt_uwb_driver/
deca_device_api.h:2380-2394`): *«On power up, or following a reset the device will progress from
INIT_RC to IDLE_RC … both INIT_RC and SPI_RDY event flags will be set»*, а `dwt_checkidlerc`
читает событие **RCINIT** (`DWT_INT_RCINIT_BIT_MASK = 0x1000000`, «Device has entered IDLE_RC»,
`deca_device_api.h:290`) в `SYS_STATUS`. Это событие выставляется **только** при переходе
INIT_RC→IDLE_RC, то есть после сброса. При первом `uwbinit` оно есть; далее `dwt_configure`
переводит чип в **IDLE_PLL** и очищает статус. На повторном `uwbinit` без сброса чип остаётся в
IDLE_PLL, нового перехода в IDLE_RC нет, RCINIT не выставляется → `dwt_checkidlerc()` всё время
возвращает 0 → ожидание истекает по таймауту (**«FAIL - IDLE_RC not reached»**). `dwreset` или
перезагрузка помогали именно потому, что заново гоняли INIT_RC→IDLE_RC.

**Что «первый этап».** Печатаемый `probe (DEV_ID)` при повторном вызове — фактически no-op:
`Dw3000Port_Probe()` кэширует результат (`if (s_probed != 0u) return 0;`) и не читает DEV_ID
повторно. Поэтому первым реально работающим этапом оказывается ожидание IDLE_RC — там и был отказ.

**Правка.** В начало `radio_init()` добавлен аппаратный сброс тем же механизмом, что `dwreset`:
- `dwreset` (команда) зовёт `uwb_hard_reset()` в `uwb_core.c` — тянет RSTn (PE10, open-drain) вниз
  на `UWB_RST_LOW_MS=2` мс, отпускает, ждёт `UWB_RST_WAIT_MS=5` мс (покрывает POR DW3000 ~1 мс +
  boot OTP ~70 мкс до готовности SPI). Это **аппаратная** часть; программную реинициализацию
  (probe/initialise/configure) выполняет сам `radio_init` дальше.
- `uwb_hard_reset()` был `static` в `uwb_core.c`. Добавлена публичная обёртка `Uwb_HardReset()`
  (guard `UWB_CHIP_DW3000`), объявлена в `dw3000_port.h`. `radio_init` зовёт её первым шагом, затем
  `spi_slow()` (INIT_RC требует SCK ≤ 7 МГц до `dwt_initialise`, UM Table 4) и `s_probed = 0u`,
  чтобы `Dw3000Port_Probe()` заново прочитал DEV_ID на свежесброшенном чипе. Дальше — существующие
  этапы IDLE_RC → `dwt_initialise` (тут драйвер сам поднимает SPI до fast 6 МГц) → `dwt_configure`.

**Счётчики (по решению владельца).** `uwbinit` сбрасывает аппаратуру и внутреннее состояние
(`s_inited`, `s_rx_armed`, `s_probed`), но **радийные счётчики не обнуляет** — их по-прежнему
обнуляет `reset` (`Dw3000Port_ResetVoiceStats`) и `uwbstat reset`. Развязка удалась без STOP:
счётчики (`cnt_tx/rx/...`) живут отдельно от флагов состояния.

## 3. Пункт 2 — взвод приёмника в конце инициализации

**Правка.** В конце `radio_init()` после `s_inited = 1u`:
```c
if (s_rx_active != 0u) { rx_arm(); }                                  /* диагностический uwbrx */
else if (Voice_IsPtt() == 0u) { rx_arm(); s_rx_armed = 1u; cnt_switch++; }  /* голос: если не PTT */
```
- взвод — существующей точкой `rx_arm()` (та же, что зовёт `Dw3000Port_VoiceRxArm`), логика не
  дублируется;
- если в момент завершения `uwbinit` **удерживается PTT** (`Voice_IsPtt()==1`) — приёмник не
  взводим: режим передачи приоритетнее, взвод произойдёт штатно на фронте PTT 1→0
  (`voice.c`: `Dw3000Port_VoiceRxArm()`), `s_rx_armed` сброшен в начале `radio_init`;
- **самовзвод в `Dw3000Port_VoicePoll` оставлен** как страховка (не заменён);
- состояние PTT берётся новой функцией `Voice_IsPtt()` (`voice.c`/`voice.h`, возвращает `g_ptt`);
  `dw3000_port.c` подключил `voice.h`;
- в ветви `LAB09_DW1000` речевого тракта нет — не затронута.

**Путь, где init успешен, а приёмник не взведён (факт из кода).** Ровно один: `uwbinit` завершился
успешно при **удерживаемом PTT** — по условию выше приёмник намеренно не взводится. Как только PTT
отпущен, `Voice_Process` на фронте 1→0 зовёт `Dw3000Port_VoiceRxArm()` → приём включается. Иных
путей нет: при `Voice_IsPtt()==0` взвод делается безусловно, плюс страховочный самовзвод в
`VoicePoll`. Это же объясняет прежнее `rx=0`/`switch=0` у слушавшей платы в прогонах: её `uwbinit`
падал на IDLE_RC (пункт 1) → `s_inited=0` → `VoicePoll` выходил в начале → приёмник не взводился.

## 4. Пункт 3 — гашение зелёного светодиода приёма

**Было.** `voice_sink()` на каждый принятый кадр делал `BSP_LED_Toggle(LED4)`. При потоке речи
(кадр каждые 20 мс) LED мерцал, а при остановке потока «залипал» в последнем состоянии (с шансом
остаться включённым) — переставал быть индикатором.

**Стало (только для UWB-транспорта, `#if VOICE_XPORT_UWB`).**
- в `voice_sink()`: `BSP_LED_On(LED4)` + запоминание `g_rxLedTick = HAL_GetTick()`, флаг `g_rxLedOn=1`;
- в `Voice_Process()` (главный цикл): если `now - g_rxLedTick >= RX_LED_ON_MS` — `BSP_LED_Off(LED4)`.
  Без блокирующих задержек, без новой работы в опросе/ISR (`voice_sink` и так в главном цикле через
  `rx_drain`);
- `RX_LED_ON_MS = 50u` — константа с комментарием, меняется одной строкой (предложение, к утверждению);
- при непрерывной речи LED горит почти постоянно (кадр каждые 20 мс < 50 мс), после прекращения
  потока гаснет за ~50 мс — «идёт приём».

**Провод (LAB07/LAB08) не затронут:** ветка `#else` сохраняет прежний `BSP_LED_Toggle(LED4)`.

## 6. Перечень фактов из кода (пп.4-5 сдачи)

- Причина отказа повторного `uwbinit` — RCINIT/IDLE_RC (см. §2, ссылки на `deca_device_api.h:290,
  2380-2394` и цикл ожидания в `radio_init`).
- `dwreset` = `uwb_hard_reset()` в `uwb_core.c` (RSTn PE10 open-drain, 2 мс низкий + 5 мс ожидание);
  переиспользован через новую обёртку `Uwb_HardReset()`.
- Единственный путь «init ok, приёмник не взведён» — удерживаемый PTT в момент завершения `uwbinit`
  (снимается штатно на отпускании PTT).
- LED4 — зелёный на STM32F411E-DISCO; прежде `BSP_LED_Toggle` на кадр в `voice_sink`, теперь
  вспышка + гашение по таймеру 50 мс из `Voice_Process` (только UWB).
