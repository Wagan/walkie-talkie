ЗАДАНИЕ (Wagan's Team): TASK_swo_trace2
Автор: Vagan Sarukhanov

КОНТЕКСТ

Демо loopback работает на обоих китах: микрофон через PDM2PCM выводится на кодек,
Fs = 16 кГц, индикация светодиодами. Проект собирается чисто.

Нужен канал вывода диагностики из платы. Выбран SWO с приёмом в SWV ITM Data Console
внутри STM32CubeIDE: вывод PB3 уже сконфигурирован как SYS_JTDO-SWO, дополнительных
выводов не требуется.

ВАЖНЫЙ РИСК. Разведка по UM1842 показала: встроенный отладчик — ST-LINK/V2 на
STM32F103C8T6, и документ говорит, что он поддерживает только SWD. Сигнал SWO заведён
на PB3 через мост SB15 (по умолчанию ON), но на разъёме CN2 соответствующий вывод
помечен как Reserved. То есть работоспособность трассировки на этой плате документом
НЕ подтверждена, и проверить это можно только опытом.

Поэтому задание разбито на две части. Часть 1 — минимальная проверка. Часть 2
выполняется ТОЛЬКО после того, как владелец подтвердит, что вывод дошёл.

SWO односторонний, только из контроллера в отладчик. Ввод команд и консольное меню
здесь не делаем — они появятся на лабораторной работе с USB Device CDC.


ПРАВИЛА (жёсткие)

1. Не гадать. Имена функций CMSIS, условия работы ITM, поля структур брать из
   фактических заголовков в проекте (core_cm4.h и соседние), а не по памяти.
2. Файл walkie-talkie.ioc не редактировать.
3. Файлы HAL, CMSIS и содержимое Drivers/BSP не изменять.
4. Правки в генерируемых файлах — только внутри блоков USER CODE.
5. Проект не собирать и не прошивать.
6. Часть 2 не начинать без явного подтверждения владельца.
7. STOP и вопрос владельцу при неоднозначности.


ЧАСТЬ 1. ПРОВЕРКА, ЧТО SWO ВООБЩЕ РАБОТАЕТ

Цель — минимальный код, по которому станет ясно, доходит ли вывод. Ничего лишнего.

A. Минимальный вывод.
   1. Файлы App/Inc/trace_swo.h и App/Src/trace_swo.c.
   2. Вывод символа в ITM штатной функцией CMSIS. По заголовку установить и записать
      комментарием в файле, что эта функция делает при выключенной трассировке или без
      подключённого отладчика: блокируется, отбрасывает символ или сразу возвращает
      управление. Это критично — прошивка должна нормально работать и без отладчика,
      иначе кит зависнет при автономном питании.
   3. Номер стимул-порта ITM вынести именованной константой.
   4. На этом этапе — только функция вывода строки. Уровней логирования, форматирования
      и подключения printf пока не делать.

B. Точка вызова.
   В Core/Src/main.c, внутри блоков USER CODE: в основном цикле выводить короткую
   строку со счётчиком, примерно раз в секунду. Из обработчиков прерываний не
   печатать ничего — они срабатывают около тысячи раз в секунду.

C. Инструкция для владельца.
   Собрать и выписать в отчёте точную последовательность для CubeIDE 1.16.0: где в
   конфигурации отладки включается Serial Wire Viewer, какое значение Core Clock
   указать (взять фактическую частоту ядра из нашей конфигурации тактирования, а не
   общее число), нужно ли задавать частоту SWO вручную и что будет при несовпадении,
   как открыть SWV ITM Data Console, какой порт разрешить и чем запускается приём.
   Формулировать по фактической документации, а не по памяти. Чего подтвердить нечем —
   так и написать.

D. Запасной вариант.
   Отдельным разделом отчёта, без реализации: если SWO не заработает, какие есть
   способы наблюдать состояние платы без остановки ядра и без дополнительного железа.
   В частности проверить по документации CubeIDE, что даёт механизм Live Expressions,
   работает ли он поверх обычного SWD и какие у него ограничения. Это нужно как
   запасной путь до появления USB CDC.

На этом Часть 1 заканчивается. Отчёт, коммит, push — и остановка.


ЧАСТЬ 2. ВЫПОЛНЯТЬ ТОЛЬКО ПОСЛЕ ПОДТВЕРЖДЕНИЯ ВЛАДЕЛЬЦА

E. Полноценный вывод.
   1. Обеспечить работу обычного printf: посмотреть, как устроен сгенерированный
      Core/Src/syscalls.c, и подключиться к нему штатным для него способом, не правя
      сам syscalls.c. Способ описать в отчёте.
   2. Дать в заголовке простой интерфейс логирования с уровнями: обычное сообщение и
      сообщение об ошибке. Без изысков, но единообразно.

F. Диагностика демо.
   В App/Src/audio_loopback.c добавить вывод, соблюдая запрет на печать из обработчиков
   прерываний:
   1. При инициализации — одно сообщение с фактическими параметрами: частота
      дискретизации, число каналов, размеры буферов, результат инициализации кодека и
      микрофона.
   2. В основном цикле, не чаще раза в секунду — строка состояния: сколько блоков
      обработано с прошлого раза, есть ли ошибка. Счётчик увеличивается в обработчике,
      печатается в основном цикле. Разделяемые переменные объявить с учётом того, что
      они меняются в прерывании.
   3. При ошибке — сообщение с указанием, какая именно функция BSP её вернула.

G. Конфигурация отладки в репозитории.
   Ранее walkie-talkie.launch не коммитился из-за абсолютного пути к файлу журнала
   ST-LINK. Проверить, можно ли задать этот путь относительным или пустым, не ломая
   конфигурацию, и как именно это сделать в IDE. Решение о коммите не принимать
   самостоятельно — подготовить вывод и оставить выбор владельцу. Ценность в том, что
   вместе с конфигурацией студент получил бы и готовые настройки SWV.

H. README.
   Короткий раздел: что такое SWO на этой плате, почему не используется виртуальный
   COM-порт (его у встроенного ST-LINK/V2 нет), и последовательность настройки из
   пункта C. Писать для студента, который делает это впервые.
