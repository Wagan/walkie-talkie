# Отчёт: вынос разбора кадра из приёмного ISR в Lab_Process (лечение)

Лечение по подтверждённому диагнозу (`docs/REPORT_rx_gaps_recon.md`,
`docs/REPORT_isr_deadline_probe.md`). Правки **только в `App/Labs/speech.c` (LAB07)** —
общий `uart_port.c` не трогался, поэтому LAB02/03/04/05 не затронуты. `.ioc`, HAL/CMSIS/BSP,
ThirdParty, приоритеты NVIC, circular-режим выхода — не трогались. Инструментовка probe A/B
сохранена полностью (нужна для сравнения до/после). Сборка LAB07: **0 ошибок, 0 предупреждений**.
На железе не проверялось — прошивает и слушает владелец.

## Замеренная причина (напоминание)

Приёмный ISR выполнял весь разбор кадра (`voice_sink`: заголовок, `Codec_Decode`, апсемплинг,
`jb_push`), `max=303 мкс`. При `NVIC_PRIORITYGROUP_0` (вытеснения нет) этот ISR, попав в окно
перед 1-мс дедлайном пере-взвода аудио-выхода (DMA NORMAL), задерживал пере-взвод ровно на свою
длительность → `probeA over=133, max=1367 мкс` → слышимые провалы. Запас на простое был всего
~13 мкс (база 1013–1018 мкс при пороге 1031). Лечение: убрать тяжёлый разбор из ISR.

## Что изменено (файл:строка)

Всё в `App/Labs/speech.c`:

- **Очередь кадров SPSC** — `speech.c:117-140`: `fq_item_t { uint16_t len; uint8_t
  data[FRAME_MAX_CONTENT]; }`, `fq[FQ_DEPTH]`, индексы `fqHead` (пишет только ISR), `fqTail`
  (пишет только Lab_Process). Счётчики `cQover` (переполнение), `loopMaxCyc` (период цикла).
- **`frame_enqueue`** — `speech.c:295-307`: новый sink для `Frame_DecodeByte`, вызывается **в
  ISR**. Только копирует байты готового кадра в слот и публикует `fqHead` (с `__DMB`). При
  полной очереди — `cQover++` и выход (никакой молчаливой потери).
- **`rx_drain`** — `speech.c:355-370`: разгрузка очереди **в Lab_Process**; для каждого кадра
  вызывает прежний `voice_sink` (тяжёлый разбор). При `ptt on` очередь опустошается
  (`fqTail = fqHead`) — без залипших кадров от прошлого сеанса.
- **Переключение sink** — `speech.c:373`: `voice_rx_byte` теперь
  `Frame_DecodeByte(&rxDec, b, frame_enqueue)` вместо `voice_sink`. В ISR остаются только SLIP+CRC
  (`Frame_DecodeByte`, дёшево) и постановка кадра в очередь.
- **Вызов разгрузки** — `speech.c:700`: `rx_drain()` в `Lab_Process` (после вычисления `g_ptt`).
- **Замер периода цикла** (probeC) — начало `Lab_Process`: макс. интервал между вызовами через
  `DWT->CYCCNT`.
- **Печать** — `speech.c:464-466`: строка `probeC offload: qover=… qdepth=… loop_max=…us` в
  команде `voice`. **Сброс** — команда `reset` (обнуляет очередь, `cQover`, `loop_max`).

`voice_sink` (`speech.c:311`) по коду не менялся — сместилось только место его вызова (из ISR в
`rx_drain`). Frame_DecodeByte (SLIP+CRC) остаётся в ISR — задача просила вынести именно разбор
заголовка/декодирование, а не кадрирование.

## Расчёт глубины очереди

- **Приток:** кадр каждые `BLOCK_MS = 5 мс` (200 кадров/с).
- **Отток:** `rx_drain` в каждом вызове `Lab_Process`. Период `Lab_Process` — **доли
  миллисекунды**: главный цикл `while(1) Lab_Process()`, а печать в консоль **полностью
  неблокирующая** (проверено по коду `console.c`): `raw_put` при полном TX-кольце **отбрасывает**
  символ (`console.c:93`), `Console_Process` делает один неблокирующий `tx_drain` = один
  `CDC_Transmit_FS` (`console.c:428`, `184`); `Console_Flush` с `HAL_Delay` в горячем пути LAB07
  **не вызывается**. Значит между двумя разгрузками накапливается **< 1 кадра**.
- **Выбор:** `FQ_DEPTH = 16` (степень двойки → маска без деления) = **80 мс** буфера. Это >16×
  запас даже против маловероятной единичной 5-мс задержки цикла. Переполнение (если запас всё же
  исчерпан) не теряется молча — считается `cQover` и печатается в `voice`.
- **Проверка на железе:** фактический максимум периода цикла печатается как `loop_max` в `voice`.
  Ожидание — сотни микросекунд, не миллисекунды. Если владелец увидит `loop_max`, сопоставимый с
  5 мс, и/или `qover>0` — сообщить, пересмотрим глубину (память позволяет: слот
  `FRAME_MAX_CONTENT=256`, `fq[16]` ≈ 4.1 КБ из ~100 КБ свободных).

## Добавленная задержка и запас джиттер-буфера

Перенос добавляет задержку = время от постановки кадра в очередь (ISR) до его разбора
(`rx_drain` в следующем `Lab_Process`) ≤ **один период `Lab_Process`** = `loop_max` (ожидаемо
доли мс). Джиттер-буфер имеет `JB_PREFILL = 320` отсчётов = **20 мс** запаса. Доли миллисекунды
≪ 20 мс — воспроизведение не голодает, `under` должен оставаться нулём. `loop_max` в `voice`
даёт владельцу прямую проверку этого неравенства на железе. Если вдруг `loop_max` окажется
соизмерим с 20 мс — **STOP и вопрос владельцу** (prefill самостоятельно не трогаю).

## Ожидаемый эффект (критерий приёмки)

Приёмный ISR теперь = `dump_put` + `Frame_DecodeByte` (SLIP+CRC, ~десятки байт) +
`frame_enqueue` (копия ≤164 байт при готовом кадре). Оценка: ~15–20 мкс против прежних 303 мкс.
Поэтому ожидается:
- `probeB rx-isr max` падает с ~300 мкс до единиц–десятков мкс;
- `probeA over` за прогон — ноль/единицы вместо 133 (пере-взвод больше не блокируется);
- `qover = 0`; `under/lost/txdrop/fe/ore` остаются нулём; на слух прерываний нет.

## Полудуплекс / PTT

- При `ptt on` `rx_drain` опустошает очередь (`fqTail = fqHead`) — принятые за время передачи
  кадры отбрасываются, на переходе `on→off` очередь пуста, залипших кадров нет.
- `voice_sink` сохраняет свою внутреннюю проверку `g_ptt` (двойная защита безвредна).
- Побочно: `recv` (инкремент внутри `voice_sink`) теперь не растёт во время `ptt on` — это
  корректнее (во время передачи приём не считаем) и не влияет на критерии приёмки.

## Память

`bss` LAB07: 20540 → **25024 Б** (+4484 = очередь `fq[16]`), из 128 КБ. `text` 85964. Запас ОЗУ
~100 КБ — без изменений по существу.

## Что потребуется для того же в LAB04 (отдельным шагом, здесь НЕ делалось)

LAB04 (`voice_wire.c`) имеет **свой** приёмный путь и джиттер-буфер (общий только слой
`audio.c`), и его `voice_sink` легче (сырой PCM, без `Codec_Decode`) — провалы там реже. Для
переноса по той же схеме нужно в `voice_wire.c`: (1) добавить такую же SPSC-очередь кадров и
`frame_enqueue`; (2) переключить его RxTap-sink на постановку в очередь; (3) вызвать разгрузку в
его `Lab_Process`; (4) добавить счётчик переполнения в его статистику; (5) те же расчёт глубины и
проверку `loop_max`. Изменения локальны в `voice_wire.c` — `uart_port.c` менять не нужно
(механизм RxTap уже общий). Делать после подтверждения эффекта на LAB07.

## Процедура проверки (для владельца)

Прогон 5 минут непрерывной передачи, **ulaw, `rate 8000`, 460800**, порядок как в
`docs/REPORT_isr_deadline_probe.md`:
1. Прошить LAB07 на обе платы, USART2 крест-накрест, наушники и USB-консоль к приёмной.
2. На приёмной: `reset`, сразу пустить непрерывную передачу, засечь секундомер.
3. Слушать 5 минут, включая минуты, где раньше был всплеск; между опросами набирать `voice`.
4. Ожидается: `probeB rx-isr max` — единицы–десятки мкс; `probeA over` — 0/единицы;
   `probeC qover=0`, `loop_max` — доли мс; `under/lost/txdrop/fe/ore = 0`; на слух чисто.
5. Если `qover>0` или `loop_max` близок к мс — сообщить (пересмотрим глубину). Если провалы
   остались при `probeB max` в единицы мкс — значит есть ещё один слой (тогда следующий вариант:
   circular-DMA выхода или приоритеты NVIC — отдельными задачами).

**STOP** — прошивает и слушает владелец; по результату решаем, нужен ли тот же перенос в LAB04 и
трогать ли circular/NVIC.
