# Отчёт: вытеснение в остальных работах курса

Обобщение лечения из `REPORT_nvic_preemption.md` на прочие работы с аудио-выходом. Перенос
`voice_sink` в очередь НЕ делался — лечит именно вытеснение (подтверждено на LAB07). Сборка всех
конфигураций (LAB00/02/03/04/05/07) — **0 ошибок, 0 предупреждений**. На железе не проверялось.

---

## Этап 1 — разведка

### 1. Какие работы нуждаются в вытеснении

Аудио-выход с 1-мс пере-взводом DMA есть только там, где компилируется `App/Common/Src/audio.c`
(он держит `BSP_AUDIO_OUT_*` + пере-взвод `BSP_AUDIO_OUT_TransferComplete_CallBack`). Его guard —
`audio.c:21`: `#if (LAB_ID == 0) || (LAB_ID == 4) || (LAB_ID == 7)`. Значит аудио-выход есть в
**LAB00, LAB04, LAB07**; в **LAB02/LAB03/LAB05 аудио-выхода нет** (эти работы `audio.c` не
компилируют — только UART/консоль) → **из задачи исключены**.

Из трёх с аудио-выходом:
- **LAB07** — уже вылечен (`a96a72f`).
- **LAB04** (`voice_wire.c`) — **нуждается**: приёмный ISR несёт весь разбор кадра
  (`voice_rx_byte`→`Frame_DecodeByte`→`voice_sink`, `voice_wire.c:190,227`) + активна консоль по
  USB, т.е. тот же тяжёлый блокирующий ISR, что срывал дедлайн в LAB07.
- **LAB00** (`stand_check.c`) — **НЕ нуждается**: это микрофон→колонки без линии, кадров и
  консоли. Конкурирующих тяжёлых ISR нет (нет USART2-приёма, нет USB OTG). Пере-взвод аудио-выхода
  может задержать лишь короткий аудио-вход (`convert_block`), а на железе LAB00-петля **уже
  проверена и идёт без провалов** (см. `REPORT_rx_gaps_recon.md`, бисекция). Плюс правило проекта
  «поведение LAB00 не менять». **Вывод: LAB00 оставляем как есть.** Если владелец захочет
  единообразия — добавить `Preempt_AudioOutHighest()` в его `Lab_Init` тривиально (LAB00 в guard
  `preempt.c` не входит, надо будет дополнить).

Итог: правка нужна **только LAB04**.

### 2. Разделяемые структуры в LAB04 (пара обработчиков иная, чем в LAB07)

В LAB04 `voice_sink`+`jb_push` остаются **в приёмном ISR** (producer), а `jb_pop`
(`Audio_FillPlayback`) — в аудио-выходном ISR (consumer). После включения вытеснения аудио-выход
(ур. 0) сможет прервать приёмный (ур. 2) **посреди `jb_push`**. Проверка по коду:

| Структура | Кто пишет / читает | Вывод |
|---|---|---|
| `jbuf` + `jbHead`/`jbTail` | producer = приёмный ISR (`jbHead`, `jb_push` `voice_wire.c:89-99`); consumer = аудио-выход ISR (`jbTail`, `Audio_FillPlayback` `:169`) | **SPSC корректен:** `jb_push` пишет `jbuf[jbHead]` и лишь ПОТОМ публикует `jbHead=nx` (`:96-97`). Если consumer прервёт producer между записью и публикацией — увидит СТАРЫЙ `jbHead` (на элемент меньше), данные уже записаны. Прерывание безопасно. **Безопасно** |
| `cOver` | только producer (`jb_push`/`jb_push_silence`) | одна сторона. **Безопасно** |
| `cUnder`, `cPlayed`, `jbPlaying`, `lastOut` | только consumer (`Audio_FillPlayback`) | одна сторона, нет RMW с producer. **Безопасно** |
| `cRecv`/`cLost`/`rxExpSeq`/`rxHaveSeq`/`rxDec` | только приёмный ISR (`voice_sink`) | consumer их не трогает; чтение в консоли — диагностическое. **Безопасно** |
| `txAccum`/`txAccN`/`txSeq` | только аудио-вход ISR (`Audio_OnCapture`/`tx_flush_frame`) | аудио-выход(0) вытесняет, но не трогает. **Безопасно** |
| `huart2` (HAL UART) | RX — приёмный ISR (ур.2); TX — `HAL_UART_Transmit_IT` из аудио-входа ISR (на передатчике, `voice_wire.c:128`) | опасно лишь если аудио-вход вытесняет USART2 → **аудио-вход и USART2/RX-DMA на ОДНОМ уровне (2)**, взаимного вытеснения нет. **Безопасно при равном уровне** |
| `hi2s` (HAL I2S) | только аудио-выход ISR (в потоке — `Audio_Init`) | **Безопасно** |
| probe A (`aoX`, audio.c) | только аудио-выход ISR | **Безопасно** |
| probe B (`rxIsrX`, uart_port.c) | только приёмный ISR | **Безопасно** |

Небезопасных структур нет. Условия те же, что в LAB07: (а) `USART2_IRQn` и `DMA1_Stream5_IRQn` на
одном уровне (приёмный колбэк не реентерабелен); (б) аудио-вход не выше USART2.

### 3. Ловушки HAL в LAB04 (обработчики выше SysTick)

Выше SysTick(1) окажется только аудио-выход(0). Его путь — `Audio_FillPlayback` (чистое чтение
`jbuf`) → `BSP_AUDIO_OUT_ChangeBuffer` → `HAL_I2S_Transmit_DMA` — только `HAL_DMA_Start_IT`, без
`HAL_GetTick`/`HAL_Delay`/ожиданий (проверено в `REPORT_nvic_preemption.md`, тот же общий код).
Аудио-вход(2) ниже SysTick: его `tx_flush_frame`→`UartPort_SendRaw`→`HAL_UART_Transmit_IT`
(`voice_wire.c:128`) неблокирующий. `cmd_send` крутит `HAL_GetTick` в потоке (`voice_wire.c:238`) —
SysTick(1) вытесняет поток, цикл прогрессирует. `HAL_Delay` в путях ISR нет. **Ловушек нет.**

### 4. Пути повторного MspInit после Lab_Init (LAB04)

Единственный — смена скорости: `cmd_baud`→`UartPort_SetBaud` (`voice_wire.c:305`)→
`HAL_UART_DeInit/Init`→`HAL_UART_MspInit` возвращает `USART2_IRQn` в (0,0). Значит после смены
baud приоритеты надо переустановить (как в LAB07). Аудио после `Lab_Init` не переинициализируется:
`Audio_Init` один раз (`voice_wire.c:387`), команды LAB04 (`send/sendbyte/stat/reset/dump/regs/
baud/voice/proto/ptt/tone`) аудио-периферию не трогают.

**Разведка чиста — переход к Этапу 2.**

### Откат

Убрать вызовы `Preempt_AudioOutHighest()` в соответствующей работе (LAB04: `voice_wire.c:411` и
`:308`; LAB07: `speech.c:672` и `:426`) — вернётся `NVIC_PRIORITYGROUP_0` и приоритеты из MspInit.
Модуль `preempt.{h,c}` можно оставить неиспользуемым. В LAB04 при откате также можно снять DWT-init
и строку probeA/сброс (не влияют на тракт).

## Процедура проверки (владелец, железо)

**LAB04** (учтено: сырой PCM 16 кГц, чистого окна по скорости нет — на 460800 запас ~1.1×, на
921600 линия сыплется, `fe=15313`). Поэтому — **короткие прогоны на 460800 с контролем счётчиков**,
а не долгое прослушивание:
1. Прошить **LAB04** обе платы, USART2 крест-накрест, **460800**. Наушники и USB-консоль к приёмной.
2. На приёмной: `reset`, затем на второй — `ptt on` (или зажать PA0), `tone on` (или голос).
3. Гонять несколько минут короткими сеансами; между ними — `voice`. Ожидается:
   - **`probeA out-rearm over=0`** (главный критерий; раньше был бы ненулевым — тот же дефект);
   - `fe`/`ore`/`lost`/`under`/`over` не растут аномально (на 460800 линия должна быть чистой);
   - на слух — тон/речь без коротких провалов, которые дал бы LAB04 без вытеснения.
4. Если `over>0` или растут `fe`/`lost` — прислать числа (возможно упёрлись в скорость линии, а не
   в дедлайн).

**LAB07** — не изменён по поведению (рефактор только вынес функцию в общий модуль). Достаточно
краткого регресс-прогона по процедуре из `REPORT_nvic_preemption.md`: `probeA over=0`.

**LAB00/02/03/05** — не затрагивались; собираются начисто. LAB00 (аудио-петля) намеренно оставлен
без вытеснения (обоснование — Этап 1 п.1).

**STOP** — прошивает и слушает владелец.
